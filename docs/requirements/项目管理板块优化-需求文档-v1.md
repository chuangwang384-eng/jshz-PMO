## 1. 背景与目标

景帅会展内部管理系统（jshz-PMO）"项目管理"板块近期上线了项目模块，在实际使用中发现三处体验与逻辑问题：

1. 项目列表页搜索区筛选项过多且控件偏宽，超出容器宽度后被换行，**"重置"按钮被挤到下一行左侧**，排版不美观；
2. **编辑已有项目时无法看到项目执行人，也无法修改/新增执行人**，与新建场景能力不一致；
3. 项目详情页阶段操作只有"切换阶段"下拉（自由跳步），**缺少面向日常使用的"推进下一阶段 / 回退阶段"明确入口**，阶段流转方向感弱。

本次改造目标：修复上述三个问题，在不改变业务规则语义的前提下提升排版、补齐编辑能力、让阶段流转更直观，并评估"回退阶段"需求的必要性与实现成本。

| R2 | 编辑已有项目支持显示与修改/新增项目执行人 | 缺陷修复 |

### 范围外（本期不做）

- 用户表新增"工号"字段及执行人下拉展示工号（成本高、收益低，仅标签展示姓名）；
- 阶段自由跳步能力的后端接口移除（保留接口能力，仅 UI 不再暴露下拉）；
- 历史项目的阶段顺序合规性回填（本期不改历史数据）；
- 取消项目按钮的样式与逻辑调整。

## 3. 现状核查结论（事实清单）

### 3.1 R1 搜索区排版

- 页面：`frontend/src/views/project/ProjectList.vue`
- 搜索区为单 flex 容器 `.toolbar-filters`（`display:flex; flex-wrap:wrap; align-items:center`），7 个筛选控件与按钮平铺：
  阶段(140px) + 开始时间(230px) + 结束时间(230px) + 负责人(140px) + 大类(110px) + 类型(130px) + 执行人(140px) + 搜索 + 重置
- 合计约 1120px 超出卡片可用宽度，`flex-wrap` 将"重置"换到第二行且左对齐。
- 项目内已有右对齐按钮组先例：`.toolbar-actions`（导出/新建/配置按钮，`justify-content: flex-end`）。

### 3.2 R2 编辑执行人

- 表结构**不缺列**：`project_executor`（project_id + user_id，唯一键 uk_project_user）；主表 Project 无 executor 字段，执行人为多对多关联表。
- 后端 update **已支持替换执行人**（`ProjectService.update()`：executorIds 非空时先删后插）。
- 根因在前端两处 + 后端返回结构一处：
  1. 详情接口 `toBriefMap()/detail()` **不返回 executorIds**；
  2. `ProjectEdit.vue` watch 填充逻辑拿不到 `executorIds`，编辑时下拉恒为空；
  3. `ProjectEdit.vue` save() 在编辑场景 `delete data.executorIds`，主动丢弃执行人。
- 执行人下拉数据来源：`GET /api/project/executors`，仅返回 `id` + `username`（username 即员工姓名）；`sys_user` 表无工号列（有 mobile/position/wecom_userid 但接口未返回）。

### 3.3 R3 阶段按钮与流转

- 页面：`frontend/src/views/project/ProjectDetail.vue` L10-19 操作区：`el-select`（目标阶段下拉）+ "切换阶段"按钮 + "编辑项目"按钮 + "取消项目"按钮。
- 阶段状态机：`project_phase` 表 6 个阶段：立项(1)/预算(2)/筹备(3)/进行中(4)/结算(5)/已完成(6)；阶段-模板绑定 `project_phase_template_rel`：立项必填 RICH_TEXT、预算必填 BUDGET、筹备选填 FILE/EXPERT/SUPPLIER、进行中/结算选填 FILE。
- 阶段变更接口：`PUT /api/project/{id}/phase` → `ProjectService.changePhase()`，**当前支持任意跳步推进与回退**，仅校验目标阶段存在/未停用/必填模板已配齐；无顺序限制；取消状态项目经 changePhase 自动恢复 ACTIVE。
- 独立取消接口：`PUT /api/project/{id}/cancel`。
- 权限：`canAdvance` = 项目负责人/执行人/超管；`canManage` = 管理员或 project:manage 权限。
- 日志：系统已有 `OperationLogService`（operation_log 表），`changePhase` 已显式记录 `ACTION_CHANGE_PHASE`，详情页时间线同源展示。复用同一接口则日志零改动。

## 5. 需求详述

### R1 列表页搜索区排版优化

**现状问题**：筛选项过多、控件偏宽，溢出换行后重置按钮被挤到第二行左侧。

**期望行为**：
1. 7 个筛选控件按目标宽度压缩（阶段 120 / 开始时间 200 / 结束时间 200 / 负责人 110 / 大类 90 / 类型 110 / 执行人 110），整体约 940px；
2. "搜索 / 重置"按钮组成独立按钮组，右对齐（复用 `.toolbar-actions` 的 `justify-content: flex-end` 模式）；
3. 在 1280px 及以上常见分辨率下，筛选区一行完整放下，不再换行。

**验收标准**：
- 1280px 宽度下筛选区单行完整展示，重置按钮与搜索按钮同行、靠右；
- 重置逻辑不变（清空筛选条件与日期区间）；
- 已有筛选功能、下拉数据不受影响。

### R2 编辑已有项目支持显示与修改项目执行人

**现状问题**：编辑已有项目时执行人下拉为空（不显示现有执行人），保存时执行人也不会被更新。

**期望行为**：
1. 打开编辑弹窗时，执行人下拉**回显当前项目已绑定的执行人**（以姓名标签展示，多人可多选）；
2. 保存时，编辑场景下提交执行人列表，后端按"删旧插新"规则替换；
3. 新建场景行为保持不变（仍提交 executorIds）。

**验收标准**：
- 编辑 A 项目（已有执行人甲、乙），弹窗回显甲、乙；
- 改为仅保留甲，保存后详情/列表显示执行人仅甲；
- 新增执行人丙，保存后执行人为甲、丙；
- 不修改执行人直接保存，执行人保持原样；
- 后端重复保存不产生脏数据（唯一键 uk_project_user 无冲突报错）。

### R3 详情页阶段按钮改造（推进下一阶段 / 回退阶段）

**现状问题**：详情页只有"切换阶段"下拉（可自由跳步），缺少明确的逐级推进/回退入口；回退能力虽在后端已存在，但 UI 语义不突出。

**期望行为**：
1. 操作区**移除目标阶段下拉与"切换阶段"按钮**，替换为：
   - **"推进下一阶段"**（primary）：点击后进入二次确认，确认后推进到当前阶段的下一个阶段；
   - **"回退阶段"**（default/warning 样式，与推进区分）：点击后进入二次确认，确认后回退到当前阶段的上一个阶段；
   - "编辑项目"、"取消项目"按钮保留原位置与样式（取消按钮样式与图标维持现状）。
2. **严格逐级**：推进只能到下一阶段（如 立项→预算）、回退只能到上一阶段（如 进行中→筹备），后端增加顺序校验，拒绝非相邻阶段变更。
3. **推进校验**：推进前校验**当前阶段必填模板已提交**（立项需 RICH_TEXT、预算需 BUDGET），未提交则推进按钮置灰并提示缺少哪些必填材料；回退不做材料校验。
4. **回退材料保留**：回退仅改变阶段状态，不删除任何已提交的模板材料；再次推进回该阶段时材料原样保留，可继续查看和编辑。
5. **二次确认**：推进/回退均弹出确认框，回退提示明确"已提交材料会保留"。
6. 已完成(6)阶段无下一阶段、立项(1)阶段无上一阶段时，对应按钮隐藏或置灰。
7. 权限沿用 `canAdvance`（负责人/执行人/超管），无权限不显示推进/回退按钮。
8. 阶段变更继续写入 operation_log（ACTION_CHANGE_PHASE），详情页时间线正常展示。

**必要性评估结论（来自方案拷问）**：
- 后端 `changePhase` 早已具备回退能力（含恢复已取消项目），"回退阶段"**不需要新增接口**，只需 UI 语义化改造 + 顺序校验，实现成本低；
- 必要性成立：当前只有下拉跳步，日常推进场景不直观、容易误选目标阶段；独立"推进下一阶段/回退阶段"按钮使流转方向明确，减少误操作；
- 建议**不做**自由跳步 UI（保留接口能力，仅 UI 不暴露），避免复杂度和误操作。

**验收标准**：
- 立项阶段点击"推进下一阶段"→ 确认 → 进入预算阶段；再次点击 → 若预算必填 BUDGET 材料未提交，按钮置灰并提示缺失材料；
- 进行中阶段点击"回退阶段"→ 确认 → 回到筹备阶段；筹备阶段已提交的材料在详情页仍可见；
- 再次推进回进行中，此前提交的材料原样保留、可编辑；
- 已完成阶段不显示推进按钮；立项阶段不显示回退按钮；
- 非负责人/执行人/超管不显示推进/回退按钮；
- 阶段变更记录出现在详情页时间线。

## 8. ADR（架构决策记录）

### ADR-001：回退阶段采用"UI 语义化改造 + 后端顺序校验"，不新增接口
- 背景：changePhase 已支持任意跳步推进/回退；
- 决策：复用 `PUT /api/project/{id}/phase`，后端增加相邻阶段校验，前端拆出两个按钮；
- 结果：日志、时间线、取消恢复逻辑零改动，实现成本最低。

### ADR-002：阶段流转收紧为严格逐级
- 背景：现状自由跳步无顺序校验，日常使用方向感弱、易误操作；
- 决策：推进/回退仅允许相邻阶段，UI 不暴露跳步下拉；接口层拒绝非相邻变更；
- 结果：业务规则更清晰；历史数据无需回填（不追溯）。

### ADR-003：执行人标签不引入工号字段
- 背景：sys_user 无工号列，执行人接口仅返回 id/username；
- 决策：编辑弹窗标签仅显示姓名（username）；
- 结果：零表结构变更、零数据补录，满足"能看清是谁"的核心诉求。

### ADR-004：回退不删除已提交材料
- 背景：回退是补救性操作，不应造成数据丢失；
- 决策：回退仅改阶段状态，材料全量保留；推进回来原样可用；
- 结果：数据安全优先，符合用户"材料依旧保存，等待推进后重启"的诉求。
