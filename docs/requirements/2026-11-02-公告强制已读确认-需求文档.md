## 1. 背景与痛点

公告模块现行语义为"查看即已读"：用户在前端点击公告条目时即调用 markRead 写入已读记录。对于制度、通知类公告，阅读不等于知悉，缺少"用户主动确认知悉"的留痕机制，无法支撑制度合规审计对"已阅读并知悉"的追溯要求。

本需求将公告区分为普通公告与强制公告两类：强制公告必须由用户点击"确认已读"后才视为已读并留痕；管理端可查询强制公告的"未确认名单"用于合规追溯。

## 3. 目标与范围（P2 收敛）

- **目标**：为公告增加"可标记为强制、可查询未确认名单"能力，实现制度公告知悉留痕；存量公告默认行为完全不变。
- **P2 范围收敛**：仅做"可标记 + 可查名单"，不做强制阻断（未确认不得继续操作）与催办（定时提醒、升级通知）。催办留作 P3。

## 4. 功能需求明细

需求编号对应已确认决策条目，逐条描述。

### 4.1 公告类型区分（决策 1、2）

公告分为普通公告与强制公告两类：

- 普通公告：维持"查看即已读"。
- 强制公告：用户必须主动"确认已读"才算已读。
- 强制公告用于制度、通知等需要合规留痕的场景；本版不提供强制阻断与催办能力。

announcement 表新增字段 require_confirm（详见设计文档），0=查看即已读，1=需确认已读；存量公告默认 0，不回填、不改变行为。

### 4.2 确认交互流程（决策 4、13）

强制公告的确认交互为"列表拦截 + 详情页确认"两段结合：

1. 用户在铃铛/全局弹窗/列表点击强制公告条目时，不立即调 markRead，先弹出确认框，文案统一为"我已阅读并知悉本公告内容"，按钮为"确认已读"；
2. 用户点击"确认已读"后调用现有已读接口（PUT /api/announcement/*/read）写已读记录，再跳转详情页；
3. 详情页内对强制公告保留"确认已读"按钮（复用现有"标记已读"按钮，改文案与语义）；普通公告维持"标记已读"；
4. 用户取消确认框则不写已读、不跳转。

伪代码（前端点击条目分支）：

```
function handleItemClick(announcement) {
  if (announcement.requireConfirm === 1) {
    const ok = showConfirm("我已阅读并知悉本公告内容", "确认已读");
    if (!ok) return;                 // 不写已读、不跳转
    await markRead(announcement.id); // 复用现有接口，幂等
  }
  openDetail(announcement.id);
}
```

### 4.3 "全部已读"排除强制公告（决策 5）

- 前端 handleMarkAllRead 仅批量标记非强制公告；
- 后端 markAllEffectiveRead 增加 require_confirm = 0 过滤；
- 强制公告必须逐条进入详情手动确认，不允许被"全部已读"一键覆盖。

### 4.4 未确认名单（决策 6、8、14）

- 复用现有 read-stats 接口的 unreadUsers 字段，不新增接口；
- 管理端统计弹窗对强制公告将"未读名单"文案改为"未确认名单"，普通公告维持"未读名单"；
- 名单能力仅 announcement:manage（与现有 read-stats 一致，绑定 ADMIN），本期只做名单查看；
- 公告下架或过期后，管理端仍可查看未确认名单做历史追溯（read-stats 现状不受上下架状态影响）。

### 4.5 已读记录语义（决策 7、10）

- announcement_read 表对强制公告仅写入"确认已读"记录，表结构、联合唯一键、幂等逻辑均不动，read_time 即确认时间；
- 强制公告未确认 = 未读（read=false），列表红点、铃铛红点、全局未读角标（30 秒轮询 unreadCount）照常计入，确认后消除；不新增独立"未确认计数"口径。

## 5. 数据治理规则（决策 11）

| 场景 | 规则 |
|---|---|
| 强制公告内容编辑后 | 清空该公告 announcement_read 记录，全员重新确认 |
| 存量公告 0→1 升级为强制 | 清空已读记录，全员重新确认 |
