## 3. 背景与目标

### 3.1 业务背景

- 客户信息板块已于 2026-10-29 由知识星球"客户喜好"子板块独立改造完成，形成独立的客户档案管理模块（客户档案、附件、关系圈、关系类型管理、关系网络图）。
- 验收中发现权限越权问题：使用普通员工（EMPLOYEE）账号登录后，在客户详情页仍可见并点击"关系类型管理"按钮，可跳转至关系类型管理页面；同款按钮在客户列表页已正确受 `customer:manage` 权限控制，详情页为改造时漏加权限指令。
- 进一步排查发现：附件下载接口对所有登录用户开放且无归属校验、无操作日志；管理页与关系图路由均无权限守卫，可通过直达 URL 访问；后端知识文档分类白名单残留 `customer-preferences` 死分类。

### 3.2 产品目标（SMART）

1. 普通员工账号在客户详情页不再看到"关系类型管理"按钮（验收口径：100% 复现路径不可见）。
2. 普通员工即使直接访问关系类型管理页 URL 也无法进入（路由级拦截）。
3. 普通员工调用 `GET /api/customer/relations/types` 返回 403，管理配置数据不外泄。
4. 客户详情页"关系圈"展示、全局关系网络图查看对普通员工保留（业务展示不收敛）。
5. 附件下载保持全员开放，但每次下载行为写入操作日志，实现可审计。
6. 清理知识文档上传接口对 `customer-preferences` 分类的残留接受能力，杜绝孤儿数据。

### 3.3 用户画像与角色

| 角色 | 权限码 | 与本次需求的关系 |
|------|--------|------------------|
| SUPER_ADMIN 超级管理员 | 全部权限码 | 不受影响 |
| ADMIN 管理员 | 含 `customer:manage` | 仍可进入关系类型管理，行为不变 |
| KNOWLEDGE_MAINTAINER 知识星球维护人 | 含 `customer:manage` | 仍可进入关系类型管理，行为不变 |
| EMPLOYEE 普通员工（默认角色） | 无业务权限码 | **本次收敛对象**：不可见按钮、不可达页面、不可调管理配置接口 |

## 4. 范围定义

### 4.1 包含范围（In Scope）

| 编号 | 功能 | 优先级 |
|------|------|--------|
| R1 | 客户详情页"关系类型管理"按钮权限收敛（补 `v-permission="'customer:manage'"`） | P0 |
| R2 | 关系类型管理路由权限守卫（直达 URL 拦截） | P0 |

| R4 | 附件下载行为操作日志埋点（下载权限保持全员开放） | P0 |
| R5 | 清理后端知识文档分类白名单中的 `customer-preferences` 死分类 | P1 |

### 4.2 不包含范围（Out of Scope）

| 项 | 说明 |
|----|------|
| 附件下载权限收敛 | 下载对全员开放是明确决策，本次不增加 `customer:manage` 校验、不做附件归属校验 |
| 关系网络图访问收敛 | 普通员工保留查看全局图与中心图，仅写操作（建关系/删关系）维持 `customer:manage` 现状 |
| 详情页关系圈收敛 | 普通员工保留查看，本次不动 |
| 查看类操作日志 | 列表/详情/关系图查看行为不入日志，避免噪音 |
| Excel 导入导出、批量操作 | 无真实诉求支撑，本次不做 |
| 客户字段脱敏 | 当前无手机号/身份证/邮箱等强敏感字段，暂不引入脱敏机制 |

### 4.3 MVP 边界

- **Must**：R1、R2、R3（权限越权闭环修复）
- **Should**：R4（下载审计）
- **Could**：R5（死分类清理）

## 5. 价值主张

| 维度 | 内容 |
|------|------|
| 现状（Before） | 普通员工可见管理按钮、可直达管理页、可调用管理配置接口；管理操作虽被页内 `canManage` 兜底挡住，但配置数据只读暴露，存在越权感知与信息泄露面 |
| 解决方案（How） | 前端按钮 + 路由 + 后端接口三层权限收敛；下载留痕；死分类清理 |
| 改变后（After） | 普通员工完全不可触达管理配置；管理操作与管理数据仅对具备 `customer:manage` 的角色开放；下载可审计 |
| 替代方案（Alternatives） | 仅补前端按钮权限（最小修复）——无法阻止直达 URL 与接口调用，不完整 |

## 7. 详细功能说明

### 7.1 R1 详情页按钮权限收敛

- **功能描述**：`frontend/src/views/CustomerDetail.vue` 中"关系类型管理"按钮补加 `v-permission="'customer:manage'"`，与列表页 `CustomerInfo.vue` 同款按钮保持一致。
- **前置条件**：用户已登录，权限指令已注册（现有 `directives/permission.js`）。
- **主流程**：普通员工进入详情页 → 按钮因无权限码被移除 DOM → 不可见不可点；具备 `customer:manage` 的用户正常可见。
- **异常流程**：权限指令未生效时按现有全局机制处理（不改变现状）。

### 7.2 R2 管理路由权限守卫

- **功能描述**：`frontend/src/router/index.js` 中 `customer-relation-type-manage` 路由增加 `meta.permissions: ['customer:manage']`。
- **前置条件**：全局路由守卫（`beforeEach`）需具备"按 `meta.permissions` 校验当前用户权限码"的通用逻辑；若现有守卫未实现，需在本次一并补充通用校验（详见设计文档 3.1）。
- **主流程**：普通员工直达该路由 → 守卫校验失败 → 重定向至无权限页/首页；具备权限的用户正常进入。
- **后置条件**：管理页仅具备 `customer:manage` 的角色可访问。

### 7.3 R3 管理配置接口收敛

- **功能描述**：`GET /api/customer/relations/types` 由"仅登录"收敛为"仅 `customer:manage`"。
- **实现要点**：
  - 后端 `CustomerController.listRelationTypes` 由 `requireUser` 改为 `requireManage`；
  - `database/migration/` 新增幂等 SQL，向 `permission` 表补充 `GET /api/customer/relations/types` 规则（type=2，code=`customer:manage`），由 `DbPermissionFilter` 兜底拦截；
  - 详情页关系圈（`GET /api/customer/{id}/relations`）与全局图（`GET /api/customer/relations/network`）保持不变，均仅登录可访问。
- **影响确认**：普通员工详情页关系圈展示不依赖 `GET /api/customer/relations/types`，本次收敛不影响其展示。

### 7.4 R4 附件下载操作日志埋点

- **功能描述**：`CustomerController` 的 `GET /api/customer/files/{fileName}` 下载成功后写入 `operation_log`。
- **实现要点**：在 `OperationLogService` 扩展客户模块动作常量（如 `DOWNLOAD_CUSTOMER_ATTACH`），下载接口在成功响应前调用 `operationLogService.record(...)`，记录用户、附件名/文件名、所属客户、IP 等。
- **边界**：本次**不**收敛下载权限、**不**做附件归属校验（决策明确：下载对全员开放）。

### 7.5 R5 清理 customer-preferences 死分类

- **功能描述**：移除知识文档上传接口对 `customer-preferences` 分类的接受能力。
- **实现要点**：`KnowledgeDocumentService.CATEGORIES` 白名单移除 `customer-preferences`；`KnowledgeDocument` 实体字段注释同步更新。仅改知识文档分类白名单，**不动** `meeting-execution`、`association-compliance`、`enterprise-compliance` 三个子板块及客户模块四表。
- **兼容性**：该分类下历史数据已于 20261029 迁移备份删除，无存量数据受影响；仅为防止未来产生孤儿分类数据。

## 14. 追加：已删除视图权限隔离（2026-11-09，1.0.37.16）

**问题**：Owner 用无「知识星球维护人」角色的账号登录，客户信息列表工具栏出现「已删除视图」开关（截图证实），可切入软删客户列表——属于 §3.1 同类漏配。

**权限口径（与既有实现一致，不新增权限码）**：已删除客户列表属于维护动作，归 `customer:manage`（ADMIN / KNOWLEDGE_MAINTAINER）。后端 `GET /api/customer` 早已在 `deleted=1` 时 `requireManage`（403），`POST /{id}/restore` 亦需 `customer:manage`，本次**未改后端**。

**前端改动**（`frontend/src/views/CustomerInfo.vue`）：
1. `已删除视图` 开关加 `v-if="canManage"`——无权限账号完全不渲染。
2. `showDeleted` 初值改为 `canManage && URL.deleted==='1'`；无权限账号即使手工访问 `?deleted=1` 也被忽略，列表按 `deleted=0` 请求，不触发 403 弹窗。
3. `syncRouteQuery` / `loadList` / `handleSwitchDeleted` 三处补 `canManage` 判断，避免状态与 URL 被绕过。
4. 操作列 `···` 菜单条件由 `canManage || showDeleted` 收紧为 `canManage`（`showDeleted` 恒蕴含 `canManage`）。

**验收**：无 `customer:manage` 账号——工具栏无开关、无新增客户/关系类型管理、列表仅正常客户、手工加 `?deleted=1` 仍为正常列表；ADMIN/维护人——开关可见、切换正常、恢复可用。
