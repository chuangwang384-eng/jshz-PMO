## 1. 总体架构（v1.0 原文 + v2.0 修订）

采用**增量扩展**方式接入现有分层，不改变知识星球既有链路：

```
[前端 EnterpriseCompliance 页]                 [个人中心页（我的待办入口）]
   ├─ MyTodoSection（我的待办区：统计卡+表格）        └─ 复用 MyTodoSection 组件（entry=personal）
   ├─ MaintenanceBoard（维护人全局看板入口，仅维护人可见）
   └─ KnowledgeDocList（原文档列表，保留 + 收藏按钮）

[后端 /api/compliance/*]                    [KnowledgeController /api/knowledge/*]
   ├─ ComplianceItemController                    ├─ 上传/更新 → 触发 ComplianceParseService
   ├─ ComplianceMyTodoController（我的待办/个人进度/提醒）├─ 收藏/取消收藏（复用 favorites 系列）
   ├─ ComplianceParseService（解析引擎）           └─ 下架/删除 → 触发事项联动
   ├─ ComplianceDueScheduler（@Scheduled 到期提醒：全局+个人）
   └─ 复用 NotificationService.notify / DbPermissionFilter / authUser.hasPermission
```

- 解析在**文档上传/更新后同步触发**（同一事务内生成草稿，或上传成功后的同一请求内完成）；
- 消息推送复用现有 `notification` 表与前端 30 秒轮询，不新增推送通道；
- 权限沿用 `knowledge:maintain`（全局维护），个人维度接口仅本人可访问；
- **我的待办聚合口径（v2.0）**：`favorites(用户收藏的知识文档)` ∩ `compliance_item(is_draft=0 且文档 status=1)`，按用户维度汇总。

## 2. 数据模型（领域建模）

### 2.1 实体关系（v2.0 修订）

```
knowledge_document 1 ── 0..n compliance_item ── 0..n compliance_item_assignee
        │ 1 ── 0..n favorites（复用现有收藏机制：user_id, document_id）
        │
        └── compliance_user_progress（user_id × item_id，个人进度/提醒/备注，仅本人）
```

### 2.2 新表：compliance_item（合规事项，v1.0 保留，v2.0 语义修订）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT PK AUTO_INCREMENT | 主键 |
| document_id | BIGINT NOT NULL | 来源文档 knowledge_document.id |
| title | VARCHAR(200) NOT NULL | 事项标题（解析自"项目"列/文本） |
| content | TEXT | 要点内容（解析自"内容"列/文本） |
| stage | VARCHAR(20) NOT NULL | 阶段枚举：INITIATION 立项 / FINANCE 财务流程 / EXECUTION 执行 / VERIFICATION 会后核销 / SPECIAL 特殊问题 / OTHER 其他 |
| time_note | VARCHAR(200) | 时间要求（文本，解析自"时间节点"列） |
| due_date | DATE NULL | 到期日期（维护人维护，可选） |
| priority | VARCHAR(10) NOT NULL DEFAULT 'MEDIUM' | HIGH / MEDIUM / LOW（维护人维护） |
| status | VARCHAR(20) NOT NULL DEFAULT 'PENDING' | 全局状态 PENDING 未开始 / IN_PROGRESS 进行中 / CONFIRMING 待确认 / COMPLETED 已完成；**v2.0：仅维护人可改** |
| is_draft | TINYINT NOT NULL DEFAULT 1 | 1=待确认草稿（解析产物）0=已发布；手动新增直接 0 |
| project_id | BIGINT NULL | 预留弱关联 project.id（本期仅存储） |
| remark | VARCHAR(500) | 备注（全局备注，维护人维护） |
| update_by | BIGINT | 最后更新人 sys_user.id |
| update_time | DATETIME | 最后更新时间 |
| last_due_notified | DATE NULL | 最近一次**全局责任人**到期提醒推送日期（去重用） |
| create_time | DATETIME | 创建时间 |

索引：`idx_document(document_id)`、`idx_status_due(status, due_date)`、`idx_stage(stage)`。

**v3.0 修订：compliance_item 新增跨版本字段**：

| 字段 | 类型 | 说明 |
|---|---|---|
| item_code | varchar(64) | 跨版本稳定标识，首次生成后固定不变（如 `EC-2026-0001`），唯一索引 |
| document_version_id | bigint | 当前所属文档版本（knowledge_document_version.id），索引 |
| previous_item_id | bigint nullable | 上一版本中同一事项的 item_id（版本血缘，首版为 NULL） |
| change_type | varchar(16) | 新增 / 修改 / 删除 / 不变；重解析时更新 |

个人进度表 compliance_user_progress 新增可选字段 `block_reason`（varchar(200)），记录阻塞原因（预设值或自定义文本）。

> v2.0 语义：该表为**全局事实**，仅维护人可写；普通用户对其的个人操作一律落 compliance_user_progress，不写本表。

### 2.4 新表：compliance_user_progress（个人进度/提醒/备注，v2.0 新增）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT PK AUTO_INCREMENT | 主键 |
| user_id | BIGINT NOT NULL | 所属用户 sys_user.id（仅本人可见） |
| item_id | BIGINT NOT NULL | compliance_item.id |
| progress_status | VARCHAR(20) NOT NULL DEFAULT 'UNPROCESSED' | 个人进度：UNPROCESSED 未处理 / PROCESSING 处理中 / COMPLETED 已完成 |
| remark | VARCHAR(500) | 个人备注（仅自己可见） |
| remind_enabled | TINYINT NOT NULL DEFAULT 1 | 个人提醒开关，默认开启 |

唯一索引：`uk_user_item(user_id, item_id)`；

> 取消收藏语义：个人进度记录**不删除**（记录保留）；我的待办聚合以收藏为入口，取消收藏即不参与聚合，重新收藏后恢复。文档永久删除时记录保留为孤儿数据（UI 不展示）。

### 2.5 收藏复用（v2.0 新增）

- 直接复用知识星球现有 favorites 机制（收藏接口/收藏列表/收藏状态），**不新增关注表**；
- 我的待办 = `SELECT item FROM compliance_item WHERE is_draft=0 AND document.status=1 AND document.id IN (SELECT document_id FROM favorites WHERE user_id=?)`。

### 2.6 解析模板配置（代码级，v1.0 保留）

`ComplianceParseConfig` 常量/枚举维护列名映射：
- Excel 固定表头映射：`时间节点 → time_note`、`项目 → title`、`内容 → content`、`备注 → remark`；
- 阶段归类关键词：立项/审批/招商→INITIATION；财务/合同/付款/发票/签署→FINANCE；执行/日程/劳务/讲题/人员→EXECUTION；核销/照片/签到/盖章/归档→VERIFICATION；特殊/区域/账户/固定劳务→SPECIAL；
- PDF/DOCX 规则解析：按段落标题与关键词抽取（规则随样本持续维护），解析失败跳过并提示手动录入。

### 2.7 跨版本匹配算法（v3.0 新增）

文档更新（新版本发布）触发重解析时，对旧版本事项集合 S_old 与新版本解析事项集合 S_new 执行匹配：

1. **第一档（自动匹配）**：标题完全一致 → 直接匹配；新事项继承旧事项的 item_code、个人进度（compliance_user_progress 按 item_code 迁移）、备注、提醒记录；
2. **第二档（待确认）**：标题归一化（去除标点/空格/中文前后缀如"关于/通知/（试行）"）后相同，或字符串相似度（编辑距离/余弦）≥80% → 进入维护人确认匹配列表；确认前个人记录保留在旧对应事项上，确认后按 item_code 合并；
3. **第三档（新增/停用）**：S_new 中无匹配 → 新增（change_type=新增，进草稿）；S_old 中未匹配 → 停用（change_type=删除，草稿确认时标记，个人记录保留、待办隐藏）；
4. 匹配结果在**草稿确认页可视化**："自动匹配 N 条 / 待确认 M 条 / 新增 X 条 / 停用 Y 条"，维护人可手动纠正映射；
5. 每次匹配确认写入 compliance_item_history（审计动作=匹配确认）。

### 2.8 完整表结构与关键索引（v3.0 新增，DDL 级）

> v2.0 已含 compliance_item / compliance_item_assignee / compliance_user_progress 三表结构；v3.0 在此给出**完整 DDL 级定义**（含 v3 新增字段与新增表），并汇总关键索引建议。

**compliance_item（合规事项主表）**

```sql
CREATE TABLE compliance_item (
  id                   BIGINT AUTO_INCREMENT PRIMARY KEY,
  item_code            VARCHAR(64)  NOT NULL COMMENT '跨版本稳定标识',
  document_id          BIGINT       NOT NULL COMMENT '所属文档',
  document_version_id  BIGINT       NOT NULL COMMENT '所属文档版本',
  previous_item_id     BIGINT       NULL     COMMENT '上一版本同一事项id（版本血缘）',
  change_type          VARCHAR(16)  NOT NULL DEFAULT '新增' COMMENT '新增/修改/删除/不变',
  title                VARCHAR(200) NOT NULL,
  stage                VARCHAR(32)  NOT NULL DEFAULT '未开始' COMMENT '全局阶段',
  priority             VARCHAR(16)  NOT NULL DEFAULT '中',
  due_date             DATE         NULL,
  time_requirement     VARCHAR(200) NULL,
  status               VARCHAR(16)  NOT NULL DEFAULT '草稿' COMMENT '草稿/已发布/停用',
  remark               TEXT         NULL,
  create_by            BIGINT       NOT NULL,
  create_time          DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  update_by            BIGINT       NULL,
  update_time          DATETIME     NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  UNIQUE KEY uk_item_code (item_code),
  KEY idx_document_version (document_version_id),
  KEY idx_status_due (status, due_date),
  KEY idx_stage (stage)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='合规事项主表';
```

**compliance_item_assignee（事项-责任人关联，v2.0）**

```sql
CREATE TABLE compliance_item_assignee (
```

**compliance_user_progress（个人进度，v2.0 + v3.0 阻塞原因）**

```sql
CREATE TABLE compliance_user_progress (
  id             BIGINT AUTO_INCREMENT PRIMARY KEY,
  item_id        BIGINT       NOT NULL,
  user_id        BIGINT       NOT NULL,
  progress_status VARCHAR(16) NOT NULL DEFAULT '未处理' COMMENT '未处理/处理中/已完成',
  block_reason   VARCHAR(200) NULL     COMMENT '阻塞原因：预设或自定义，v3.0',
  remark         VARCHAR(500) NULL     COMMENT '个人备注（仅本人可改）',
  remind_enabled TINYINT      NOT NULL DEFAULT 1,
  remind_days_before INT      NOT NULL DEFAULT 3,

  UNIQUE KEY uk_item_user (item_id, user_id),

```

```sql
CREATE TABLE compliance_reminder_log (

```

## 3. 后端设计

### 3.1 新增接口（/api/compliance，Controller 内部鉴权；v2.0 修订）

| 接口 | 说明 | 权限 |
|---|---|---|
| GET /api/compliance/items | 全局事项列表：documentId/stage/status/priority/keyword 筛选 + 分页 | 登录（普通用户只读；维护人可看草稿） |
| GET /api/compliance/my-todo | **（v2.0 新增）我的待办**：统计（todoCount/nearDueCount/overdueCount）+ 列表（事项/来源文档/阶段/优先级/时间要求/到期/我的进度/提醒），按到期升序、高优置顶 | 本人（登录即可） |
| PUT /api/compliance/my-progress/{itemId} | **（v2.0 新增）个人进度更新**：progress_status / remark | 本人 |
| PUT /api/compliance/my-reminder/{itemId} | **（v2.0 新增）提醒设置**：remind_enabled / remind_days | 本人 |
| POST /api/compliance/items | 手动新增事项（全局） | knowledge:maintain |
| PUT /api/compliance/items/{id} | 编辑事项（维护人全字段；**v2.0：不再开放责任人改全局状态**） | knowledge:maintain |
| DELETE /api/compliance/items/{id} | 删除事项 | knowledge:maintain |
| POST /api/compliance/items/confirm | 批量确认草稿（解析产物 → 发布，发布后通知关注者） | knowledge:maintain |

| GET /api/compliance/items/{itemId}/assignee-progress | 某事项全部责任人个人进度（只读） | knowledge:maintain |
| GET /api/compliance/users/{userId}/progress | 某责任人全部事项个人进度聚合（只读） | knowledge:maintain |

### 3.2 解析服务 ComplianceParseService（v1.0 保留 + v2.0 发布同步）

- `parseAndCreateDrafts(document, file)`：按文件类型分发：
  - xlsx/xls：Apache POI 读取，按表头映射 + 阶段归类生成草稿；
  - PDF/DOCX：文本抽取（pdfbox / poi-tl 或 docx4j）+ 规则解析；
  - 其他：返回未解析标记。
- 上传/更新文档接口（KnowledgeController）在保存文档后调用本服务，返回"已解析 N 条草稿"；
- 文档更新：先标记旧事项为待替换（隐藏），确认新草稿后删除旧事项；
- 草稿确认发布（confirm）：**v2.0 追加**——发布后查询收藏该文档的用户列表，逐个写入/更新其 compliance_user_progress（若无记录则创建 UNPROCESSED 行），并推送 `compliance_published` 通知；
- 文档下架：批量隐藏（查询 join knowledge_document.status=1 过滤），我的待办聚合自然失效；
- 文档永久删除：删除该文档全部事项与责任人；个人进度记录保留（孤儿数据不展示）。

### 3.3 我的待办与个人进度服务（v2.0 新增）

`ComplianceMyTodoService`：
- `listMyTodo(userId)`：按收藏文档聚合已发布事项，join compliance_user_progress 返回个人字段（未建档的项按 UNPROCESSED/提醒默认开渲染）；
- `updateMyProgress(userId, itemId, status, remark)`：INSERT ON DUPLICATE KEY UPDATE，仅写个人维度；
- `updateMyReminder(userId, itemId, enabled, days)`：同上；
- 所有方法强制 `WHERE user_id = 当前登录用户`，杜绝越权读取他人个人数据。

### 3.4 定时任务 ComplianceDueScheduler（v2.0 修订：全局 + 个人）

- `@Scheduled(cron="${expert.compliance.due-cron:0 30 8 * * ?}")`，开关 `expert.compliance.due-enabled`（默认 true，参照 WecomSyncScheduler 模式）；
- **全局责任人提醒（保留）**：每日扫描 `status != COMPLETED AND due_date IS NOT NULL AND (due_date <= today+N 且 last_due_notified < today)`，推送全部责任人（assignee），提前 N 天（默认 3）+ 到期当天各一次；
- **个人提醒（v2.0 新增）**：扫描 `compliance_user_progress p JOIN compliance_item i WHERE p.remind_enabled=1 AND i.status != COMPLETED AND i.due_date IS NOT NULL AND i.due_date <= today+p.remind_days AND (p.last_due_notified IS NULL OR p.last_due_notified < today)`，按个人 remind_days 提前天数 + 到期当天各推送一次；
- 推送后更新各自 `last_due_notified = CURDATE()`（全局字段与个人字段分开去重）。

### 3.5 消息类型（v2.0 修订）

NotificationService 新增常量：`compliance_published`、`compliance_updated`、`compliance_due`；
jump_path：`/knowledge-planet/enterprise-compliance`；
前端 `MessageCenter.vue` TYPE_LABELS 同步补充三类映射；
个人提醒推送 content 注明"（个人提醒，提前 X 天）"，与全局责任人提醒文案区分。

### 3.6 权限落地（v2.0 修订）

- 后端：全局编辑类操作 `authUser.hasPermission("knowledge:maintain")`；个人维度接口强制 `userId == currentUserId`；
- 前端：维护人看板入口 `v-permission="'knowledge:maintain'"`（无权限则不渲染）；我的待办区全员可见；个人操作按钮始终可用；
- 不改 DbPermissionFilter、不新增权限码。

### 3.7 状态流转规则（v3.0 新增）

**全局状态四态（compliance_item.status / stage 语义组合）**：未开始 → 进行中 → 待确认 → 已完成。

| 规则 | 说明 |
|---|---|
| 仅维护人可变更 | 全局状态（四态）仅 knowledge:maintain 权限可操作（推进/回退均逐级校验） |
| 个人进度三态 | 未处理 → 处理中 → 已完成；**仅本人可变更** |
| 维护人只读 | 维护人可查看个人进度，不可修改个人备注与进度 |
| 个人不影响全局 | 个人修改个人进度不影响全局状态 |
| 完成联动 | 某事项**所有责任人**个人进度均已完成 → 给维护人发消息中心提醒"可评估是否更新全局状态"；**不自动改**全局状态 |
| 阻塞语义 | 标记阻塞原因时个人进度按"处理中"语义统计，但列表单独展示阻塞标识 |

**个人进度状态流转**（个人三态）：

```
未处理 --本人--> 处理中 --本人--> 已完成
处理中 --本人--> 未处理（撤销）
已完成 --本人--> 处理中（撤回，需原因可填）
```

**全局状态流转**（维护人四态）：

```
未开始 --维护人--> 进行中 --维护人--> 待确认 --维护人--> 已完成
任意态 --维护人--> 回退到上一级（严格逐级校验，参照项目板块 changePhase 模式）
```

### 3.8 提醒幂等与异常处理（v3.0 新增）

- **写入即幂等**：每次计划提醒先向 compliance_reminder_log 插入一行（唯一约束 user_id+item_id+reminder_type+scheduled_time，`INSERT IGNORE`/捕获 DuplicateKey 后视为已计划）；
- **发送幂等**：定时任务扫描 send_status='PENDING' 且 scheduled_time 到期的行；发送成功后置 SENT；**同节点只发一次**，任务重复执行/并发不会重复推送；
- **自然日计算**：scheduled_time 按自然日（当天 00:00/定时点）计算；表结构预留 workday_only 字段（工作日计算下轮实现）；
- **异常矩阵**：
  | 场景 | 处理 |
  |---|---|
  | 事项已完成 | 不再生成/取消 PENDING 提醒（SKIPPED） |
  | 事项停用/删除 | 停止提醒（SKIPPED） |
  | 到期日期修改 | 按新日期重算，旧节点置 SKIPPED，不重发 |
  | 取消收藏 | 暂停个人提醒（保留 log，后续不再触发） |
  | 重新收藏 | 恢复提醒 |
  | 用户关闭提醒 | 不再推送（remind_enabled=0，日志 SKIPPED） |
  | 定时任务重复/并发 | 唯一约束幂等，只发一次 |
  | 消息发送失败 | retry_count+1，允许重试，**上限 3 次**，达上限置 FAILED 不再重试 |

### 3.9 事项修改历史（v3.0 新增）

- compliance_item_history 记录关键字段变更：标题 / 阶段 / 优先级 / 责任人 / 时间要求 / 到期日期 / 状态；
- 审计动作：草稿发布 / 下架 / 恢复 / 删除 / 匹配确认（field_name 存动作名，old/new 存状态快照）；
- 责任人变更：写历史（field_name=责任人，old=旧责任人，new=新责任人）+ 通知新责任人（消息中心"你被设为 XX 事项责任人"）；旧责任人记录保留、不通知；
- 匹配确认：写历史（field_name=匹配确认，old=旧 item_id，new=新 item_id）。

## 7. 风险与对策（v2.0 修订）

| 风险 | 对策 |
|---|---|
| PDF/DOCX 文本抽取规则不稳定 | 解析失败静默跳过、手动录入兜底；规则按样本持续维护；配置开关可整体关闭自动解析 |
| 解析草稿误上架 | 草稿态（is_draft=1）强制确认后才发布 |
| 重复推送（全局/个人） | 全局 last_due_notified 与个人 last_due_notified 分别去重 |
| 个人数据越权读取 | 个人接口强制 user_id=当前用户；查询恒带用户维度 |
| 收藏数据量大 | 我的待办分页 + 排序限流；收藏走现有索引 |
| 多文档事项量大 | 分页 + 视图切换 + 搜索筛选 |
| 影响现有知识星球功能 | 只新增表/接口/组件，收藏原样复用，不动原表结构与接口行为；文档下架/删除联动在原有逻辑处追加 |
| 前端多次构建覆盖 | 所有前端改动完成后只做最后一次 build，再重启 Nginx |
| 存量事项无 item_code | 迁移先回填生成，再建唯一索引；回填失败不建索引（阻断） |
| 匹配算法误判 | 自动匹配仅限标题完全一致；归一化/相似度档一律人工确认；确认动作可审计 |
| 提醒重复发送 | compliance_reminder_log 唯一约束 + SENT 状态幂等；并发任务只发一次 |
| 提醒无限重试 | retry_count 上限 3 次，达上限置 FAILED 停止 |
| 历史数据量膨胀 | compliance_item_history 按 item_id+操作时间索引，常规量级可接受 |

## 8. ADR 记录（v1.0 ADR-001~008 保留，v2.0 追加 ADR-009~015）

| ADR | 决策 | 理由 |
|---|---|---|
| ADR-001 轻量看板而非完整事项管理 | 本轮做看板 + 待办，预留扩展 | 匹配知识库定位，避免与项目/审批模块职责重叠 |
| ADR-002 后端同步解析 + 草稿确认 | 上传时后端解析，草稿确认发布 | 稳定、与上传流程衔接；避免错误数据直接上架 |
| ADR-003 解析覆盖 xlsx + PDF/DOCX | 表格解析 + 文本抽取规则解析 | 文件格式多样，需覆盖主流格式；图片等手动录入 |
| ADR-004 复用 knowledge:maintain | 不新增权限码 | 保持轻量，避免权限体系膨胀 |
| ADR-005 复用现有消息中心 | notify() + 前端轮询 | 零新增推送通道，改动最小 |
| ADR-006 到期提醒 last_due_notified 去重 | 字段级记录推送日期 | 简单可靠，支持"提前 N 天 + 到期当天"规则 |
| ADR-007 事项隐藏=文档下架联动 | 查询 join 文档状态 | 无需额外字段，数据保留可恢复 |
| ADR-008 预留 project_id + 多责任人 | 弱关联，本期仅存储 | 后期与项目管理联动免返工 |
| ADR-009 收藏即关注 | 复用现有 favorites 机制，不新建关注表 | 零新增概念与表结构，收藏习惯天然匹配"关注"语义 |
| ADR-010 个人进度独立表 | compliance_user_progress 存 user×item 个人数据 | 与全局 compliance_item 解耦，多人个人视图互不影响 |
| ADR-011 个人修改仅自己可见 | 个人接口强制本人维度；不改全局表 | 满足数据隔离，避免个人操作污染全局事实 |
| ADR-012 个人提醒默认开启 + 可调整 | 每项 remind_enabled/remind_days 默认开、提前3天 | 默认体验好，又允许个性化 |
| ADR-013 取消关注保留记录 | 取消收藏不删个人进度，重新收藏即恢复 | 避免二次收藏后进度丢失 |
| ADR-014 维护人看板仅维护人可见 | 前端 v-permission + 后端 knowledge:maintain | 职责隔离，普通用户界面保持简单 |
| ADR-015 全局状态与个人进度分离 | 全局 status 仅维护人改；个人 progress_status 三档 | 明确"全局事实"与"个人视图"职责边界 |
| ADR-016 责任人自动待办 | 我的待办 = 收藏事项 ∪ 责任人事项；收藏=关注机制不变 | 被指为责任人即使未收藏也应获得待办（D24） |
| ADR-017 跨版本稳定标识 | item_code 稳定 + document_version_id / previous_item_id / change_type 版本血缘；三档匹配 | 文档更新重解析时个人记录不丢（D25/D26） |
| ADR-018 匹配可视化 | 草稿确认页显示 自动匹配N/待确认M/新增X/停用Y，可手动纠正 | 模糊匹配必须人工兜底，可审计（D27） |
| ADR-019 个人记录生命周期 | 收藏关系与个人记录彻底分离；停用隐藏保留、恢复还原 | 展示与业务历史解耦，防误删（D28） |
| ADR-020 维护人只读进度 | 按事项/按责任人只读查看；个人备注不可改；阻塞原因单独展示 | 数据隔离 + 可运维平衡（D29） |
| ADR-021 完成提示联动 | 所有责任人完成→仅提醒维护人评估，不自动改全局状态 | 全局状态仍由维护人决策（D30） |
| ADR-022 提醒幂等 + 历史 | reminder_log 唯一约束幂等、重试上限；item_history 字段变更+审计动作 | 并发/重跑只发一次，变更可追溯（D31/D32） |

## 9. 词汇表（v2.0 修订）

| 术语 | 含义 |
|---|---|
| 事项（Compliance Item） | 合规文档中拆解出的单条执行要求/注意事项（全局事实） |
| 草稿（Draft） | 自动解析产物，is_draft=1，需维护人确认后发布 |
| 关注（收藏） | 复用知识文档收藏机制；收藏某文档=关注该文档，其事项进入我的待办 |
| 我的待办（My Todo） | 我收藏的全部文档的已发布事项合集（个人维度） |
| 个人进度 | compliance_user_progress 中本人对某事项的 未处理/处理中/已完成 三档状态，仅自己可见 |
| 个人提醒 | 个人维度到期提醒：默认开、提前3天+到期当天，可每项关闭/调整 |
| 全局看板 | 维护人可见的全局事项管理界面（上传解析→草稿确认→字段维护） |
| 责任人 | compliance_item_assignee 关联的用户（全局字段，维护人维护） |
| 到期提醒 | 定时任务在到期前 N 天/当天向责任人（全局）或本人（个人）推送的站内通知 |
