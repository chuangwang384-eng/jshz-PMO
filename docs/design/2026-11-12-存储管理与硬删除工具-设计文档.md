# 存储管理与硬删除工具 — 设计文档（2026-11-12）

## 1. 背景与目标
项目资料库采用"软删留痕"设计（`ProjectService.deleteDoc` 置 `is_deleted=1`，普通附件物理文件永不删除；日程附件仅在全库无引用时物理删），导致 `<LOCAL_PATH>` 等存储目录只增不减。本设计提供**管理员级存储管理工具**：存储占用统计与预警、孤儿文件清理、预览缓存清理、已取消/已删除项目的关联数据硬删除，目标是防止存储空间耗尽，同时不破坏现有软删留痕与引用共享语义。

## 2. 硬删除适用范围（明确清单）
### 2.1 不受影响（保留）
- 操作日志 `operation_log`、下载留痕 `download_log`（审计底线）
- 审批单 `application`/`approval_record`（项目引用在 biz_data JSON 内，仅作历史留痕，不随项目删除）
- 知识文档库 `knowledge_document` 及文件、专家主数据、客户/供应商主数据、合规模板文档（`compliance_item` 按 projectId 硬删的是**项目维度的候选/待办数据**，模板主数据 `documentId` 维度不动）

### 2.2 项目硬删除：随项目一并硬删的关联数据（同一事务）
| 类别 | 表 | 删除键 |
| --- | --- | --- |
| 分阶段资料（含软删行） | project_doc | project_id |
| 日程文件与记录 | project_schedule | project_id |
| 参会专家/候选 | project_speaker | project_id |
| 项目-专家关联（劳务费） | project_expert | project_id |
| 项目-供应商关联 | project_supplier | project_id |
| 合同快照 | project_contract | project_id |
| 阶段流转历史 | project_phase_history | project_id |
| 执行人/协助人 | project_executor / project_assistant | project_id |
| 合规待办推送 | compliance_project_todo | project_id |
| 合规文档绑定 | compliance_project_doc_binding | project_id（主键） |
| 合规执行清单 | compliance_execution | project_id |
| 执行任务/事件/提醒 | compliance_execution_task / _event / _reminder | execution_id ∈ 该项目执行清单 |
| 合规事项（项目维度候选） | compliance_item | project_id |
| 事项责任人/隐藏/历史/进度 | compliance_item_assignee / _hide / _history / compliance_user_progress | item_id ∈ 该项目事项 |
| 项目主行 | project | id |

### 2.3 物理文件删除
- 收集范围：project_doc.filePath（含软删）∪ project_schedule.filePath ∪ project_contract.filePath（合同文件同存项目资料库）。
- 时机：DB 事务提交后（`afterCommit`）；删除前对每个文件**再查一次全库引用**（project_doc/project_schedule/project_contract 任意表仍引用则跳过物理删，防共享引用误删，口径与 `ScheduleParseService.deleteScheduleDoc` 一致）。
- 物理删除经 `ProjectStorageService.deleteFile`（防穿越校验）。

## 3. 孤儿文件清理（防存储爆炸的核心）
- 扫描对象：项目资料库目录下全部文件（`project_*.<ext>` 与 `_richtext/*.json`）。
- 孤儿定义：存储键不在 project_doc.filePath ∪ project_schedule.filePath ∪ project_contract.filePath 全表（**含软删行**）引用集合中。
- 清理：POST 带 expectedCount+expectedBytes 集合版本校验（服务端重扫描，任一不符返回 409），逐文件物理删除，操作日志留痕。**孤儿文件本身已无任何业务引用，硬删不影响任何在线功能。**

## 4. 存储占用统计与预警
- GET /api/storage-admin/stats：按目录统计（项目资料库、知识文档库、预览缓存、照片库、照片库临时、客户附件库、供应商图库）字节/文件数；另报磁盘剩余空间。
- 阈值：`expert.storage.warn-threshold-bytes`（默认 10GB）/ `expert.storage.critical-threshold-bytes`（默认 20GB），按单目录大小判 NONE/WARNING/CRITICAL，整体取最高级；前端以标签+颜色预警。

## 5. 权限与操作确认机制
- 新权限码 `storage:manage`（菜单 MENU + 接口 type=2 八条路径，含 v2 全目录孤儿 2 条），绑定 ADMIN 角色；SUPER_ADMIN 代码内全权。后端每个端点先 `hasPermission("storage:manage")`。
- 三档确认：
  1. 孤儿清理/缓存清理：`ElMessageBox.prompt` 输入固定确认词 + expectedCount/expectedBytes 服务端校验；
  2. 项目硬删除：仅限 `status ∈ {CANCELED, DELETED}` 的项目；页面展示关联数据计数明细；`ElMessageBox.prompt` **输入完整项目名**方可执行；
  3. 全部写操作记 `operation_log`（新增 ACTION_STORAGE_PURGE_ORPHANS / ACTION_STORAGE_CLEAR_PREVIEW / ACTION_STORAGE_PURGE_PROJECT）。
- 不可恢复提示：所有删除按钮旁与确认弹窗明示"**永久删除，不可恢复**"。

## 6. 接口契约
| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | /api/storage-admin/stats | 各目录占用 + 阈值级别 + 磁盘剩余 |
| GET | /api/storage-admin/project-orphans | 孤儿文件清单（名称/大小/时间）+ 总计 |
| POST | /api/storage-admin/project-orphans/purge | {expectedCount, expectedBytes} → 删除数/字节 |
| POST | /api/storage-admin/preview-cache/purge | {expectedCount} → 清空预览缓存（可再生成） |
| GET | /api/storage-admin/orphans | 全目录孤儿清单（scope 缺省 all；返回各目录 items/count/bytes） |
| POST | /api/storage-admin/orphans/purge | {scope, expectedCount, expectedBytes} → 删除数/字节 |
| GET | /api/storage-admin/projects/{id}/purge-preview | 硬删预览（项目名/状态/可删性/各类计数/文件数与字节） |
| POST | /api/storage-admin/projects/{id}/purge | {confirmName} → 各类行删除计数 + 文件计数/字节 |

## 6.1 全目录孤儿清理（v2 扩展，2026-11-12 已发布 1.0.38.17）
Owner 追加需求："正常的（其他）孤儿文件也要能清理"。孤儿判定从项目资料库单目录扩展为 6 个可清理目录，引用集合按目录定义（DB 存纯文件名，扫描键=相对路径，命中 key 或文件名即视为被引用）：

| scope | 目录 | 引用集合（含软删/历史行，保守保留） | 排除规则 |
| --- | --- | --- | --- |
| project | 项目资料库 | project_doc ∪ project_schedule ∪ project_contract 的 filePath | 无 |
| knowledge | 知识文档库 | knowledge_document.file_path ∪ knowledge_doc_version.file_path | `_preview/` 子目录（预览缓存走专用清空） |
| photo | 照片库 | expert.photo / id_card_front / id_card_back | `richtext_*` 富文本内嵌图（引用在正文 JSON/HTML，无法按文件名反查） |
| photo-tmp | 照片库临时 | 全部 application.biz_data 中的 `TMP:<文件名>` | 无 |
| customer | 客户附件库 | customer_attachment.storage_name | 无 |
| supplier | 供应商图库 | supplier_image.file_name ∪ 兼容 supplier.images JSON 数组 | 无 |

实现要点：
- `StorageAdminService.OrphanSpec`（scope/name/root/refs/skipPreviewDir/skipRichtextImages）统一描述各目录；`orphansOf(scope)`、`allOrphans()`、`purgeOrphans(scope,expected...)`、`deleteWithin(root,key)` 复用同一套扫描与防穿越删除。
- 前端页面改为可展开表格：一次扫描 6 个目录，逐目录展示孤儿数与可释放容量，按目录清理（固定确认词 + expected 校验 + 刷新复核）。
- 新增迁移 `20261112_add_storage_orphan_scopes_permission.sql`（2 条接口权限，幂等，绑定 ADMIN）。

## 6.2 已删除资料文件回收（v3，2026-11-12 已发布 1.0.38.18）
现象：清理孤儿后项目资料库仍有大量文件。根因：普通孤儿口径把软删行（`project_doc.is_deleted=1`）也计为引用，故"删除资料"只留 DB 行、文件永久驻留（实测 27 个 / 109.2 MB）。

方案：新增范围 `project-deleted`（展示名「项目资料库（已删除资料）」）：
- 候选 = `project_doc.file_path` 中**全部行均软删**、且**无任何未删引用**（`is_deleted=0` 的资料 ∪ 日程 ∪ 合同）的路径；
- `is_deleted IS NULL` 视为未删（历史行保守保留）；
- 只删磁盘文件，**保留 DB 行/删除人时间/操作日志**（审计不受影响）；系统本无资料恢复入口；
- 复用 `/orphans`、`/orphans/purge`（expected 校验 + 防穿越 + STORAGE_PURGE_ORPHANS 日志），**无新增权限路径、无数据库迁移**。

## 7. 风险与回滚
- 项目硬删除**不可逆**：无软删兜底，唯一"恢复"途径是数据库备份（`scripts/backup.ps1` 惯例）；设计上以状态白名单（仅 CANCELED/DELETED）+ 完整项目名确认 + 权限码收敛风险。
- 孤儿清理风险低（无引用），但若未来新增"文件直存项目资料库"的表而未纳入引用集会误判——设计要求新增存储引用方必须同步加入扫描引用集合（文档已注明）。
- 预览缓存清理零风险（按需再生成）。
- 回滚：撤代码即可；迁移 SQL 仅 INSERT IGNORE 权限行，回滚为对应 DELETE（文档附）。
