# 项目管理模块「基本信息」改版 设计文档

## 1. 数据层

### 1.1 project 表新增列（迁移 `20261109_project_basic_fields.sql`，幂等）

```
team              VARCHAR(20)  NULL  -- DEPT1/DEPT2/DEPT3，必填由服务层校验
city_id           BIGINT       NULL  -- supplier_city.id，逻辑外键
meeting_start_date DATE        NULL  -- 单日=与结束同日
meeting_end_date   DATE        NULL
client_company    VARCHAR(200) NULL
client_name       VARCHAR(100) NULL
remark            VARCHAR(500) NULL
+ KEY idx_project_team(team)、idx_project_city(city_id)
```

复用列语义变更：`name`=会议名称、`category`=会议类型、`start_date/end_date`=项目起止（服务层改必填）。列保持 NULL 允许是为了迁移幂等与旧路径兼容，必填约束统一在 `ProjectService.create/update` 校验。

### 1.2 project_assistant 新表

```
id BIGINT PK AUTO_INCREMENT
project_id BIGINT NOT NULL
user_id    BIGINT NOT NULL
create_time DATETIME DEFAULT CURRENT_TIMESTAMP
UNIQUE uk_pa_project_user(project_id, user_id)、KEY idx_pa_user(user_id)
```

实体 `ProjectAssistant` + `ProjectAssistantMapper`（MyBatis-Plus 常规注册，无需额外配置）。

### 1.3 数据清理（一次性）

由 `scripts/apply-migration-20261109-project-rebuild.ps1` 执行：每表先 `CREATE TABLE IF NOT EXISTS *_bak_20261109 LIKE` + 首次备份 INSERT，再 DELETE；合规执行只删 `project_id IS NOT NULL` 行；操作日志只删 `target_type='PROJECT'`。完成后写标记表 `mig_20261109_project_reset_done`，重复运行自动跳过清理、仅重放幂等 DDL——防止发布后误清新数据。

## 2. 服务层（ProjectService）

| 点 | 设计 |
|----|------|
| 团队校验 | `TEAM_LABELS` 固定枚举 Map；create 必填、update 传入即校验 |
| 城市校验 | `supplierCityMapper.selectById`，不存在报「请从城市字典中选择」 |
| 起止必填 | create 强制；`end < start` 拦截 |
| 举办时间 | 两值可空；`end < start` 拦截；update 单边修改时与库内另一边联合校验 |
| 负责人 | create 缺省取 `user.getUserId()`（全员可选；原 9 个 null 报错路径删除） |
| 协助人 | `saveAssistants(projectId, ids)` 全量替换；create 允许空；update 以 `body.containsKey("assistantIds")` 判定显式提交（数组可空=清空） |
| 列表输出 | `toBriefMap` 增 `teamLabel`（服务端翻译）/`cityName`（省级前缀，直辖市只显示市名）/`assistantNames/assistantIds` |
| 筛选 | `keyword` 对 name/clientCompany/clientName 三列 `and(or(...))` 模糊；`team`/`cityId` 等值；`assistantId` 仿执行人先查关系表再 `in` |

## 3. 控制器

`GET /api/project`、`GET /api/project/export` 各新增 4 个可选参数（keyword/team/cityId/assistantId）透传服务层；导出表头扩为 20 列（会议名称/类型/团队/城市/起止/举办/负责人/协助人/执行人/客户单位/客户姓名/类型/阶段/状态/预算/备注/创建时间等）。

## 4. 前端

- **ProjectList**：列与筛选按需求文档 §2 重做；查询状态 `router.replace` 写回 URL（keyword/team/cityId/status/ownerId/assistantId/category/typeId/executorId/startEnd/endBegin-endEnd/page/pageSize，默认值不写）；城市下拉 `listSupplierCities()` 一次拉全量 349 市按省分组；行点击进详情；删除改 MessageBox 确认（沿用 1.0.37.14 的教训，不用 popconfirm）。
- **ProjectEdit**：720px 弹窗，12 项字段 + 保留的类型/阶段/执行人；城市按省分组 filterable；总负责人默认 `authStore.id`；编辑回显 `assistantIds`；提交 body 含全部新字段。
- **ProjectDetail**：四张信息卡重排（项目属性含团队/城市；人员卡增协助人头像串；时间卡含举办时间单日/区间展示；客户与状态卡）；`remark` 独立备注卡（有值才显示）。

## 5. 权限与兼容

- 权限零新增：写操作仍 `project:manage` / 创建 `project:create`；行级可见性（负责人/执行人）不变。
- **旧前端调新后端**：新增参数全部可选、新列 NULL 兼容，旧页面不炸。
- **新前端调旧后端**：发布顺序为迁移→后端→前端，且新列表会请求 `keyword` 等参数——旧后端不认识的可选参数被 Spring 忽略，返回无新字段时前端显示 `—`，不白屏。

## 6. 风险与回滚

| 风险 | 缓解 |
|------|------|
| 数据误清 | 全量备份表 + 标记表防重跑；备份可 `INSERT ... SELECT` 回原表 |
| 旧代码路径写 project 漏 team | 列允许 NULL + 服务层集中校验；当前唯一写路径是 create/update |
| 导出列偏移 | 表头与单元格同一常量数组顺序生成 |

回滚：后端 `backend/releases/` 上一版 jar 蓝绿回切；前端 `scripts/rollback-frontend.ps1`；数据库新列可 `ALTER TABLE project DROP COLUMN ...` + `DROP TABLE project_assistant`（旧代码忽略新列，也可不回滚）。
