## 1. P1-2：账号停用/删除后 Token 仍可用

### 1.1 现状与证据

- `security/JwtAuthenticationFilter.java`：只校验 JWT 签名与 `userId/username/roles`，不查询 `sys_user.status`，不校验用户是否仍存在。
- `security/AuthUser.java`：`isEnabled()`、`isAccountNonLocked()` 恒为 `true`。
- `security/JwtTokenProvider.java`：`expire-hours: 8`，无 `tokenVersion`、黑名单或吊销机制。
- `service/UserService.java`：`updateUser`（停用）、`deleteUser`、`resetPassword`、`assignRoles` 均未使已签发 Token 失效；`deleteUser` 未清权限缓存。
- `service/ContactSyncService.java`：企微同步停用账号（约 141、185 行）只改 `status`，不处理已登录会话。
- 权限缓存 `PermissionService` 仅提供全量 `clearCaches()`，没有按用户失效能力。

**结论**：停用/删除后，旧 Token 在 8 小时有效期内仍可通过 `authenticated()`；角色变更虽清权限缓存，但 Token 本身仍有效。

### 1.2 改动文件/类

| 文件 | 改动 |
| --- | --- |

| `mapper/SysUserMapper.java` | 新增原子自增 `bumpTokenVersion(Long id)` |

| `security/JwtAuthenticationFilter.java` | 校验 `tv`、用户存在性、`status=1`；短 TTL 状态缓存；不满足则不建立认证 |
| `service/UserAuthStateService.java`（新增） | 用户状态 + tokenVersion 的 60 秒 TTL 缓存；`get`/`evict`/`bumpAndEvict` |

| 测试（新增） | `UserAuthStateServiceTest`、`JwtTokenProviderTest` |

### 1.3 具体做法

1. **数据库**：`sys_user.token_version` 默认 0；迁移脚本按列存在性判断，支持重复执行。
2. **签发**：`createToken(..., long tokenVersion)` 写入 `tv`；`AuthService.buildLoginResponse` 读取用户当前版本。
3. **校验**：过滤器解析 `tv` 后：
   - `tv` 缺失 → 视为旧版 Token，**不建立认证**（走 401）；
   - 查询 `UserAuthStateService`：用户不存在、`status != 1`、`tokenVersion != tv` → 不建立认证；
   - 查询异常 → 记录 WARN，不建立认证（fail-closed）；
   - 通过 → 构造 `AuthUser(..., enabled=true)`。
4. **缓存**：`UserAuthStateService` 使用 `ConcurrentHashMap`，TTL 60 秒（`expert.auth.state-cache-seconds`）。停用/删除/改密/改角色时立即 `evict`，因此单实例部署下**下一次请求即失效**；多实例部署下最迟 60 秒。缓存只存 `exists/status/tokenVersion`，不含敏感信息。
5. **失效动作**：
   - `updateUser`：更新后 `bumpAndEvict` + `clearCaches`；
   - `deleteUser`：删除后 `evict` + `clearCaches`（行不存在即拒绝）；
   - `resetPassword`：重置后 `bumpAndEvict`；
   - `assignRoles`：分配后 `bumpAndEvict` + `clearCaches`；
   - `changePassword`：更新密码后 `bumpAndEvict`，并用新版本重新签发 Cookie；
   - `ContactSyncService` 停用/启用账号：`bumpAndEvict`。
6. **AuthUser**：6 参构造保留（`enabled=true`），新增 7 参构造供过滤器使用；`isEnabled()`/`isAccountNonLocked()` 返回真实值。

### 1.4 存量 Token 处置策略

- 上线前签发的 Token **不含 `tv` claim**，统一按“旧版 Token”处理：不建立认证，返回 401，前端跳转登录页。
- 影响：部署后所有已登录用户需**重新登录一次**；有效期 8 小时，不存在长期影响。
- 原因：若把缺失 `tv` 当作 0 放行，则停用账号的旧 Token 仍可继续使用至过期，无法达成本次修复目标。
- 回滚兼容：旧版后端不识别 `tv` claim，会忽略该字段；回滚后新 Token 仍可正常解析，无需清理 Token。

### 1.5 影响范围与兼容性

- 新增数据库列，旧代码忽略该列，向后兼容。
- 登录响应体结构不变；Token 增加一个 claim。
- 改密接口仍返回 `{code:0}`，但会额外下发新 Cookie；前端无需改动。
- 停用/删除/改密/改角色会使旧会话失效，属于预期安全行为。
- `AuthUser` 保留原构造，现有测试与 `ComplianceV4AccessService` 不需要改动。

### 1.6 验证方式

- `mvn -o -q -DskipTests compile` 编译通过。
- 单元测试：
  - `JwtTokenProviderTest`：签发/解析 `tv`；缺失 `tv` 返回 null。
  - `UserAuthStateServiceTest`：缓存命中只查一次、`evict` 后重新查询、用户不存在返回 `exists=false`。
- 手动验证（未执行时明确标注）：
  1. 登录获取 Cookie；
  2. 管理员停用该账号；
  3. 原 Cookie 立即请求 `/api/auth/me` → 401；
  4. 重新启用并可登录；
  5. 改密后旧 Cookie 失效、新 Cookie 可用。
- 数据库：执行迁移后 `SHOW COLUMNS FROM sys_user LIKE 'token_version'`。

### 1.7 回滚点

- 代码回滚到 `b221ad4`；`token_version` 列可保留（旧代码忽略），无需删列。
- 若必须删列：先确认无新版本代码运行，再执行 `ALTER TABLE sys_user DROP COLUMN token_version`（非必要，不建议）。
- 回滚后用户无需再次登录（旧 Token 含 `tv` 也能被旧代码解析）。

## 2. P1-5：知识文档下载不校验上下架状态

### 2.1 现状与证据

- `controller/KnowledgeController.java:216` `GET /api/knowledge/docs/files/{fileName}`：仅 `storageService.resolveDocument(fileName)` 校验路径，未校验文档 `status`。
- `service/KnowledgeDocumentService.findByFilePath` 已存在，但仅在下载审计与预览时调用，未做授权判断。
- 下架（`status=0`）只影响 `pageList`，文件流仍可直接访问。
- 文件名规则 `doc_<时间戳>_<原文件名>` 可预测/可传播，旧链接在撤权后继续有效。

### 2.2 改动文件/类

| 文件 | 改动 |
| --- | --- |
| `service/KnowledgeDocumentService.java` | 新增 `canAccessFile(doc, user)` 与 `requireDownloadable(storedName, user)`；不存在返回 404，无权限返回 403 |
| `controller/KnowledgeController.java` | 文件流入口先调用 `requireDownloadable`，复用返回的文档做审计与预览；移除重复 `findByFilePath` |
| 测试（新增） | `KnowledgeDocAccessPolicyTest`：上架可读、下架仅维护人可读、不存在拒绝 |

### 2.3 具体做法

1. 在服务层集中授权，避免控制器散落判断：
   ```java
   public static boolean canAccessFile(KnowledgeDocument doc, AuthUser user) {
       if (doc == null) return false;
       if (user != null && user.hasPermission("knowledge:maintain")) return true;
       return Integer.valueOf(1).equals(doc.getStatus());
   }
   ```
2. `requireDownloadable`：
   - 文档不存在 → `BusinessException(404, "文档不存在或已删除")`；
   - 无权限 → `BusinessException(403, "文档已下架，暂不可访问")`；
   - 通过 → 返回文档，供审计/预览复用。
3. 控制器在**任何文件流返回之前**执行校验（下载、`preview=true`、旧版 inline 预览三条路径统一）。
4. 未知文件（数据库无记录）一律 404，避免孤儿文件绕过授权。
5. 下架/永久删除无需额外清理：状态判断在每次请求时实时进行，旧链接立即失效。

### 2.4 影响范围与兼容性

- 上架文档行为不变；普通用户访问下架文档由“可下载”变为 403，符合安全预期。
- 维护人（`knowledge:maintain`）保持可访问下架文档，便于复核/重新上架。
- 下载审计仍只在 `download=1` 时记录，行为不变。
- 预览接口的错误响应由全局异常处理返回 `{code,message}`，前端已有失败提示逻辑。

### 2.5 验证方式

- 单元测试覆盖三种状态。
- 手动验证（未执行时标注）：
  1. 维护人上传文档并下架；
  2. 普通用户访问 `/api/knowledge/docs/files/{fileName}?download=1` → 403；
  3. 维护人访问 → 200；
  4. 上架后普通用户访问 → 200。

### 2.6 回滚点

- 回滚 `KnowledgeController` 与 `KnowledgeDocumentService` 到 `b221ad4` 即可；无数据库变更。
- 回滚后下架文档重新变为“登录即可下载”，需知悉该风险。

## 3. P2-7：大文件上传内存与阻塞风险

### 3.1 现状与证据

- `KnowledgeController.update`：`file.getBytes()` 读取最大 50MB 文件，随后同步调用 `complianceService.parseAndCreateDrafts(...)`。
- `KnowledgeDocumentService.upload`：同样 `file.getBytes()`；`textExtractor.extract(file)` 内部 `file.getBytes()`。
- `KnowledgeDocTextExtractor.extractStructured(byte[], ...)` 对 PDF 逐页 OCR（Tesseract，单页最长 45 秒），全程同步占用请求线程。
- `ComplianceService.parseAndCreateDrafts` 标注 `@Transactional`，长事务包含解析/OCR。
- `DocPreviewService` 转换有超时与缓存，但仍在请求线程同步执行。

### 3.2 改动文件/类

| 文件 | 改动 |
| --- | --- |
| `database/migration/20261106_add_knowledge_parse_status.sql`（新增） | `knowledge_document` 增加 `parse_status`、`parse_message`、`parse_time` |
| `entity/KnowledgeDocument.java` | 新增三个解析状态字段 |
| `common/KnowledgeParseStatus.java`（新增） | `PENDING/RUNNING/SUCCESS/FAILED` 常量 |
| `config/KnowledgeAsyncConfig.java`（新增） | `knowledgeParseExecutor`：core 2 / max 4 / queue 100 / AbortPolicy |
| `service/KnowledgeParseTaskService.java`（新增） | `@Async` 执行正文抽取与合规解析；状态落库；版本一致性保护；失败记录 |
| `service/KnowledgeDocumentService.java` | 上传/更新不再同步抽取正文、不再 `file.getBytes()`；初始化解析状态 |
| `controller/KnowledgeController.java` | 上传/更新成功后触发异步任务；移除同步合规解析块；拒绝任务时标记失败 |
| `service/KnowledgeDocTextExtractor.java` | 新增基于 `Path`/`InputStream` 的抽取，避免 `byte[]` 副本 |
| `service/ComplianceParseService.java` | 新增基于 `Path` 的 xlsx 解析重载 |
| `service/ComplianceService.java` | 新增基于 `Path` 的 `parseAndCreateDrafts` 重载，复用原逻辑 |
| `resources/application.yml` | 新增 `expert.knowledge.parse.*` 线程池参数 |

### 3.3 具体做法

1. **流式落盘**：上传仍由 `KnowledgeDocStorageService.saveDocument` 使用 `Files.copy(file.getInputStream(), ...)`，不读取 `byte[]`。
2. **异步任务**：
   - 上传/更新事务提交后（控制器在服务返回后调用），提交 `docId + version` 到 `knowledgeParseExecutor`；
   - 任务内先置 `RUNNING`，从磁盘路径抽取正文，再按分类执行合规解析；
   - 成功置 `SUCCESS` + 消息 + 时间；异常置 `FAILED` + 截断消息，写 ERROR 日志。
3. **版本一致性**：所有状态/正文更新都带 `WHERE id=? AND version=?`；若用户已上传新版本，旧任务不得覆盖新版本状态或正文，且跳过合规草稿生成。
4. **正文抽取**：`KnowledgeDocTextExtractor` 增加 `extract(Path, fileName)`：
   - PDF：`PDDocument.load(path.toFile())`；
   - DOC：`WordExtractor(Files.newInputStream(path))`；
   - DOCX：`XWPFDocument(Files.newInputStream(path))`；
   - 其他格式返回 null，不报错。
5. **合规解析**：`ComplianceParseService` 增加 `parse(..., Path, textContent)`；xlsx/xls 从 `Files.newInputStream` 读取，pdf/docx 继续使用已抽取正文。`ComplianceService` 增加 Path 重载，事务边界不变（在异步线程内开启）。
6. **线程池**：core 2 / max 4 / queue 100 / `AbortPolicy`；拒绝时同步标记 `FAILED` 并返回上传成功（文件已保存），不阻塞请求线程。
7. **状态字段**：`parse_status`（VARCHAR(16)）、`parse_message`（VARCHAR(500)）、`parse_time`（DATETIME）。图片等无需抽取的格式直接 `SUCCESS`，消息“图片无需正文提取”。
8. **预览**：`DocPreviewService` 保持同步（需要即时返回），但已有缓存、单文档锁、超时与重试；本次不改变其接口契约，仅记录为后续可选优化。

### 3.4 影响范围与兼容性

- 上传/更新响应结构不变；新增 `parseStatus/parseMessage/parseTime` 字段。
- 正文检索（C1）在异步任务完成后可用，通常为秒级；解析期间 `content` 为空，搜索暂不命中该文档。
- 企业合规事项由“上传后立即可见”变为“解析完成后可见”；`parseStatus` 可供前端提示（本次不改前端）。
- 旧数据 `parse_status` 为 NULL，视为“历史数据未记录状态”，不影响读取。
- 异步任务与请求线程使用同一数据库，版本条件更新避免覆盖。
- 新增线程池仅在知识库上传/更新时使用，不与其他异步任务混用。

### 3.5 验证方式

- 编译与单元测试。
- 手动验证（未执行时标注）：
  1. 上传 20-50MB PDF，请求在数秒内返回，`parse_status=PENDING/RUNNING`；
  2. 等待后查询列表，`parse_status=SUCCESS`，`content` 非空；
  3. 上传企业合规 xlsx，任务完成后生成草稿事项；
  4. 解析期间再次上传新版本，旧任务不得覆盖新版本状态/正文；
  5. 模拟解析异常（损坏文件），`parse_status=FAILED` 且有 `parse_message`，上传仍成功。
- 日志检查：无 `OutOfMemoryError`，请求线程不出现长时间占用。

### 3.6 回滚点

- 代码回滚到 `b221ad4`；新增列可保留（旧代码忽略）。
- 回滚后恢复同步解析；已处于 `PENDING/RUNNING` 的记录不会被旧代码更新，可人工重置为 NULL 或忽略。
- 若需彻底清理：停用异步线程池后删除三列（非必要）。
