## 1. 总体设计概览

```
审批人 → 审批管理页（我的待办）
          ├─ 筛选区：申请类型多选 + 提交时间范围 + status + keyword
          ├─ 列表：复选框列（仅当前页勾选）
          ├─ 顶栏：批量通过 / 批量驳回（未勾选时禁用）
          ├─ 二次确认弹窗：数量 + 类型分布（批量驳回时填公共意见）
          └─ 批量接口（整体事务 + 逐条校验 + 部分成功明细）
                ├─ 批量通过 → 逐条 approveCreate/approveContract/approveModify
                ├─ 批量驳回 → 逐条 reject + 清理临时照片 + 公共意见
                └─ 结果 → 逐条写 approval_record（批量审批）+ 逐条发 TYPE_APPROVAL_RESULT
```

- 无数据库表结构变更（复用现有字段 `current_assignee` / `extra_approver` / `status` / `application_type` / `create_time`）。
- 权限沿用 `approval:audit`，无新权限点、无新角色。

## 2. 后端设计

### 2.1 待办列表查询改造（`ApplicationService.listRequests()`）

现状（L322-344）：仅 status/statuses + keyword 过滤，全员可见同一批待办。

改造后过滤条件（在 service 层叠加当前登录用户）：

```
WHERE status = 0
  AND (current_assignee IS NULL
       OR current_assignee = :currentUser
       OR extra_approver = :currentUser)
  [AND application_type IN (:types)]      -- 新增：类型多选，空则不限制
  [AND create_time >= :startTime]         -- 新增：时间范围起
  [AND create_time <= :endTime]           -- 新增：时间范围止
  [AND (biz_data 申请人/专家名 LIKE :keyword)]
ORDER BY create_time DESC
```

- 保持分页结构不变（`orderByDesc(createTime)`）。
- 已处理页（statuses='1,2,3'）不增加 assignee 过滤，仍按多状态统一分页展示。

### 2.2 批量通过接口

```
POST /api/audit/batch-approve
Body: { "ids": [1, 2, 3, ...] }          // 上限 50
Resp: {
  "successIds": [1, 3],
  "failItems": [ { "id": 2, "reason": "单据已被其他审批人处理" } ]
}
```

处理流程：
1. 权限校验：`hasPermission(PERM_APPROVAL_AUDIT)`。
2. 入参校验：ids 非空、去重、数量 ≤ 50。
3. 整体事务内逐条处理：
   - `getPending(id)` 乐观防重（仅 status=0 可处理）；
   - `checkAssignee(id, currentUser)` 归属校验（共享池/转办/加签三者并集规则）；
   - 按 `application_type` 分派 `approveCreate / approveContract / approveModify`；
   - 写 `approval_record`（action=APPROVE，node_name=「批量审批」，comment 可空）；
   - 发 `TYPE_APPROVAL_RESULT` 通知给申请人。
4. 单条失败不中断整批，捕获后记入 failItems（失败原因：已被处理 / 归属不符 / 类型分派异常等）。
5. 事务提交；部分成功明细返回前端。

### 2.3 批量驳回接口

```
POST /api/audit/batch-reject
Body: { "ids": [1, 2, ...], "comment": "公共意见（必填，≤200字）" }
Resp: 同批量通过（successIds / failItems）
```

处理流程：
1. 权限校验同上。
2. 入参校验：ids 非空去重 ≤50；comment 非空、长度 ≤200。
3. 整体事务内逐条处理：
   - `getPending(id)` 防重 + `checkAssignee(id, currentUser)` 归属校验；
   - 复用单条 `reject()` 逻辑（清理临时照片、`addRecord("批量驳回","REJECT", comment)`）；
   - 发 `TYPE_APPROVAL_RESULT` 通知给申请人。
4. 部分失败明细返回，同 2.2。

### 2.4 Controller 层（`AuditController.java`）

- 新增 `POST /api/audit/batch-approve`、`POST /api/audit/batch-reject` 两个接口方法。
- 复用现有权限注解（`@PreAuthorize("hasAuthority('approval:audit')")` 或项目既有方式）。
- 参数用 `@RequestBody` DTO：`BatchApproveDTO` / `BatchRejectDTO`（ids + comment）。
- 返回统一响应体包装 `BatchAuditResult`（successIds / failItems）。

### 2.5 审批记录与通知

- `approval_record`：逐条写入，`node_name` = 「批量审批」，`action` = APPROVE / REJECT，`operator` = 当前用户，`comment` = 公共意见（批量驳回时）。
- 通知：逐条调用现有 `TYPE_APPROVAL_RESULT` 通知逻辑，标题/内容沿用单条审批文案，可在内容中标注「已批量处理」。

### 2.6 权限设计

- 前端：`ApprovalManage.vue` 页面级 `v-permission="'approval:audit'"` 不变；批量按钮不新增权限指令。
- 后端：批量接口沿用 `PERM_APPROVAL_AUDIT` 校验。
- RBAC：无新增 SQL；与 20261031 已修复的转办/加签权限保持三方一致。

## 5. 错误处理与部分成功

| 场景 | 处理 |
|---|---|
| 单据已被处理（status≠0） | 该条失败，原因「单据已被处理」，不整批回滚 |
| 归属不符（转办/加签给别人） | 该条失败，原因「无权审批该单据」 |
| 批量驳回 comment 为空/超长 | 整体参数校验失败，返回 400，前端提示 |
| ids 为空 / 超 50 | 整体参数校验失败，返回 400 |
| 类型分派异常 | 该条失败，原因「处理失败：<异常摘要>」，不中断整批 |
| 部分失败 | 返回 `successIds` + `failItems`，前端刷新后失败项仍留在待办列表 |

## 6. 风险与回滚

| 风险 | 等级 | 缓解措施 |
|---|---|---|
| 批量误操作（批量通过错误单据） | 中 | 强制二次确认弹窗；勾选仅当前页；全部三类允许但弹窗展示类型分布 |
| 并发重复审批 | 中 | 沿用 `getPending()` 乐观防重；批量内逐条校验 |
| 批量驳回放宽意见必填语义 | 低 | 公共意见必填 + 限 200 字 + 逐条留痕，满足合规 |
| 待办隔离改变现有「全员可见」习惯 | 低 | 转办/加签归属单原本点击即被拦截，改造后仅收敛展示，不改变审批权 |

回滚预案：
- 前端：关闭批量按钮入口、撤销筛选字段即可回退交互层；
- 后端：批量接口为**新增接口**，不修改现有单条接口；列表过滤可下线参数开关回退；
- 数据库：无 schema 变更，无迁移回滚负担。

## 7. 测试要点

| 用例 | 验证点 |
|---|---|
| 待办隔离 | 共享池 / 转办给我 / 加签给我三类单据均展示；转办给别人的单据不展示 |
| 批量通过 | 多类型混合勾选通过；结果置已通过；approval_record 逐条留痕；申请人收到通知 |
| 批量驳回 | 公共意见必填、限 200 字；单据置已驳回；临时照片清理；留痕与通知正确 |
| 部分成功 | 混入已被他人处理的单，返回 successIds + failItems，失败原因正确 |
| 防重 | 同一单据并发两次批量/单条审批，仅一次成功 |
| 筛选叠加 | 类型多选 + 时间范围 + keyword 叠加过滤正确，翻页正常 |
| 权限 | 无 approval:audit 用户不可见入口、批量接口返回 403 |
| 归属兜底 | 归属不符单据在批量中返回失败原因 |
