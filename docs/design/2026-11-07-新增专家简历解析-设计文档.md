# 新增专家·简历解析设计

日期 2026-11-07 · 状态：已评审（Owner 决策确认） · 版本 v1.1 · 关联需求：[2026-11-07-新增专家简历解析-需求文档](../requirements/2026-11-07-新增专家简历解析-需求文档.md)

核心原则：**复用既有 OCR/抽取基础设施、数据不出内网、解析结果仅作候选、失败不阻塞手动流程、简历原文不留存**（AGENTS.md 第 6 节）。

**Owner 决策（2026-11-07）**：使用本项目既有 Tesseract OCR（企业合规/知识星球链路）→ 图片简历纳入支持；头像=候选+用户确认；解析范围=姓名/单位/头像+顺带命中的科室/职称/联系方式；语义理解本期以多策略本地解析实现，LLM 增强另立需求（需求 §5-4）。

## 2. 后端设计

### 2.1 解析接口

`POST /api/experts/resume/parse`（multipart，字段 `file`）：

1. 校验：扩展名白名单 pdf/doc/docx/ppt/pptx/jpg/png；≤20MB；登录即可。
2. 文本获取（按类型分发）：
   - **pdf**：PDFBox 文本层；若每页平均文本 <20 字符（扫描件），`PDFRenderer` 栅格化前 3 页 → `ocrPage` 逐页 OCR 合并。
   - **doc/docx/ppt/pptx**：POI 抽取（复用既有逻辑）。
   - **jpg/png**：`ImageIO.read` → `ocrPage(image, false)`。
3. 图片候选抽取：PDF 内嵌图（PDResources）/docx（XWPFPicture）/ppt（XSLFPictureShape）；jpg/png 整图即唯一候选。过滤（80×80~1500×1500、宽高比 0.5~1.8、>5KB）排序取前 3，转 ≤200KB JPEG base64。
4. 全程内存/临时文件，请求结束删除临时文件（复用 ocrPage 既有的临时文件清理模式）。
5. 返回 `{ fields: {姓名,单位,科室,职称,联系方式}, photoCandidates: [...], hitCount, message }`（fields 只含命中字段）。

### 2.2 字段解析（ResumeParseService，多策略本地解析）

按行拆分（OCR 文本先清理坐标残片），**多策略按优先级组合**，首个可信命中即停：

| 字段 | 策略（依次降级） |
| --- | --- |
| 姓名 | ① `姓名/Name` 标签行；② 首行 2~4 汉字且不含通用词（简历/个人/求职/专家） |
| 单位 | ① `单位/工作单位/任职单位/所在单位` 标签行；② 含机构后缀词表（医院/研究院/研究所/大学/学院/中心/公司）的首个短行（≤30 字）；③ 含"医院"且含地名前缀的行 |
| 科室 | ① `科室/所在科室/部门` 标签行；② 含科室词表（科/病房/中心/办公室/部）且长度 ≤20 的行，跳过已命中单位的行 |
| 职称 | ① `职称/专业技术职务/职级` 标签行；② 职称词表精确匹配（主任医师/副主任医师/主治医师/住院医师/研究员/副研究员/教授/副教授/高级工程师/主任药师/副主任药师/主管药师/药师/主管技师/技师/主任护师/副主任护师/主管护师/护师/护士…） |
| 联系方式 | 全文正则：手机号 `1[3-9]\d{9}`（首个）→ 邮箱（首个） |

- 词表集中为常量，便于后续 LLM 策略替换（策略接口 `ResumeFieldStrategy` 预留）。
- OCR 文本置信度低：匹配失败的行做一次去空格重试；仍失败即留空，不猜测。
- 整体超时 8s（不含 OCR 单页 45s 上限；OCR 页数限前 3 页）。

### 2.3 审计

`OperationLogService` 记录：操作人、原始文件名（不含路径）、文件大小、格式、字段命中数、耗时。**不记录解析出的字段值与简历内容**。

## 3. 前端设计

- 弹窗顶部（三类照片上传区上方）增加「上传简历自动解析」行：`el-upload`（accept=".pdf,.doc,.docx,.ppt,.pptx,.jpg,.png"，auto-upload=false）+「开始解析」按钮 + 状态文案（解析中/成功 N 字段/失败原因）。
- 响应处理：
  - `fields` 仅填充**当前为空**的表单字段；已填字段不动（不覆盖）。
  - 填充的字段 label 旁显示小字「来自简历」标记（仅表单态样式）。
  - `photoCandidates` 横向缩略图 + 「使用此照片」；点击后构造 File 对象走既有 `onPickPhoto('photo', …)` 数据流（审批归档链路不变）。
  - 失败/超时：红色提示原因 + 重新解析；不阻塞手动填写与提交。
- OCR 场景耗时较长：按钮 loading 态 + 文案「识别中，扫描件约需 10~45 秒」。

## 5. 风险与兼容

- **OCR 质量**：Tesseract 对拍照模糊/艺术字识别率有限——字段留空即人工补填，产品定位"候选 + 人工确认"。
- **语义理解边界**：多策略本地解析覆盖规范简历；自由格式可能漏抽。LLM 语义增强为后续独立需求（本地部署 vs 外部 API，Owner 拍板后另立设计）。
- **Tesseract 依赖**：本机已安装（企业合规链路在用）；若服务迁移需同步部署 Tesseract 与 chi_sim 语言包，`/health` 不涉及。
- **性能**：图片/扫描件解析受 OCR 限制（每页 ≤45s，限 3 页）；前端明确提示耗时。
- **隐私**：简历不落盘（OCR 临时文件由既有 finally 清理）、日志不含内容、候选图片仅返回当前用户。
