## 1. 设计目标与约束

- 复用现有数据，不新增业务表。
- 日历的可见范围不得扩大项目详情的查看范围：日历只给出日期、项目名、负责人，详情仍走原有校验。
- 迁移向后兼容（README R-3）；`init.sql` 与 `migration/` 同步，`check-schema-parity.ps1` 通过。
- 前端遵循 AGENTS.md 第 17 节样式令牌、第 18 节硬编码禁令、第 19 节复用规范；撞期、角色、日期展开等规则只保留一处实现。
- 不引入第三方日历库，用 Element Plus 加自绘组件。

## 4. 数据设计

**4.1 不新增业务表。** 数据全部来自 `project`、`project_assistant`、`project_executor`、`profile_department`、`profile_membership`、`sys_user`。

**4.2 索引（可选）。** 日历查询条件是状态加日期区间重叠，建议加 `KEY idx_project_meeting (status, meeting_start_date, meeting_end_date)`。当前数据量下不加也能用，放在二期迁移里顺带做。

**4.3 会议日期必填。** 列保持可空，只在应用层校验。原因：存量项目、已删除项目和历史项目可能为空，改成 NOT NULL 会让迁移失败或需要填占位日期。

**4.4 team 与组织架构同步。**

- 映射规则：组织架构节点的 `seed_key` PROJECT\_1 → DEPT1，PROJECT\_2 → DEPT2，PROJECT\_3 → DEPT3。
- 派生规则：取负责人的 `profile_membership` 所在部门，沿 `parent_id` 向上找到第一个能映射的节点。映射不到时的取值见需求文档 8.3。
- 写入时机：创建项目、变更负责人时派生；员工调岗时，由 `ProjectTeamSyncService` 对该员工名下状态为 ACTIVE 的项目重算；另加每日兜底任务，参照现有调度器（如 `ComplianceDueScheduler`）。
- 收口：团队标签映射合并到一处，`ProjectService` 与 `DashboardReadService` 都引用它。
- 迁移：回填前先建备份表（沿用 `*_bak_*` 命名），回填产出差异清单，回滚可从备份表恢复。

## 5. 接口设计

**5.1 日历接口**

`GET /api/project/calendar?scope=me|dept&from=YYYY-MM-DD&to=YYYY-MM-DD`

- `from` 到 `to` 最多 62 天，超出返回 400。
- `scope=me`：返回我作为负责人、协助人、执行人的项目。
- `scope=dept`：服务端判断调用人是否为某个 `profile_department.leader_user_id`，不是则 403；部门范围由服务端算，**不接受前端传部门**。
- 过滤：`status = 'ACTIVE'`、会议日期非空、与 `[from, to]` 区间重叠。
- 字段白名单：`projectId`、`name`、`ownerName`、`meetingStartDate`、`meetingEndDate`、`roles[]`，部门范围另含 `userId`、`userName`、`disabled`。不返回预算、客户、专家、阶段、文件等任何其他字段。
- 同一人在同一项目多个角色时合并为 `roles[]`，前端按负责人、协助人、执行人的优先级展示。
- **有意不套用** `appendRowLevelCondition`：日历可见范围大于详情可见范围，这是需求 C6 的明确要求，也是本设计最需要安全评审的一点。

**5.2 工作台**

`/api/dashboard/overview` 的 `sections` 新增 `myMeetings`（所有人）、`deptMeetings`（仅部门负责人，其余人省略该 section）。沿用现有 `capabilities` 与 `reads.allowed` 机制。

**5.3 详情**

不变。`GET /api/project/{id}` 仍经 `requireProjectReadable`，无权限返回 403。

**5.4 权限点**

- 在 permission 表新增 `GET /api/project/calendar` 的路径规则，权限码建议 `project:calendar`，绑定默认员工角色，迁移用 `INSERT IGNORE` 保证幂等。也可以复用既有读权限码，**待核实**现有读权限的绑定对象后定。
- `/api/project/calendar` 与 `/api/project/{id}` 同级，须用测试确认字面路径优先、不被当作 id 解析。

## 6. 查询设计

```sql
SELECT p.id, p.name, p.meeting_start_date, p.meeting_end_date,
       ou.username AS owner_name, r.user_id, r.role
FROM project p
JOIN (
  SELECT id AS project_id, owner_id AS user_id, 'OWNER' AS role FROM project
  UNION ALL SELECT project_id, user_id, 'ASSISTANT' FROM project_assistant
  UNION ALL SELECT project_id, user_id, 'EXECUTOR' FROM project_executor
) r ON r.project_id = p.id
JOIN sys_user ou ON ou.id = p.owner_id
WHERE p.status = 'ACTIVE'
  AND p.meeting_start_date <= :to AND p.meeting_end_date >= :from
  AND r.user_id IN (:userIds)
```

- `scope=me` 时 `userIds` 只含当前用户。
- `scope=dept` 时，部门范围在 Java 里计算：读出组织树（约 20 个节点，`ProfileOverviewService` 已有读取逻辑可复用），从调用人负责的部门起收集部门及下级，再取这些部门的 `profile_membership` 成员。树很小，不用递归 CTE。
- 创建人不单独计入，按已确认的三类角色口径。
- 同项目多角色在 Java 里合并。

## 7. 前端设计

- **URL 回存**：`?view=calendar&month=2026-12&scope=dept`，参照 `SupplierList.vue` 的 `initFromRoute`、`syncRouteQuery` 模式。
- **月历**：七列网格，多日会议在每个日期格都出现；同人同日两个及以上项目标“撞期”。
- **部门排期**：员工为行、日期为列，横向滚动容器，首列固定，周末和今天有标识；格子显示角色字，撞期显示“!”；点格子弹出当天会议列表。
- **角色表达**：文字标记（负/协/执）加颜色，颜色用新增令牌 `--ui-role-owner`、`--ui-role-assist`、`--ui-role-exec`，同步写暗色值，不硬编码。
- **详情跳转**：弹窗先显示日期、项目名、负责人，“查看详情”进入 `/project/:id`，由后端 403 兜底，前端不预判权限，避免前后端判断不一致。
- **工作台面板**：需在四处同步注册——`DashboardController.SECTIONS`、`DashboardLayoutService` 白名单、`DashboardView.vue` 面板配置与默认布局、前端 `allSections`。**待核实**：已保存了自定义布局的用户如何合并新面板，需先读 `20261106_dashboard_layout_v2` 的兼容策略。
- **立项表单**：`ProjectEdit.vue` 会议起止日期标必填并前端校验；团队下拉改为只读展示由负责人派生的结果。
- **响应式**：≤768px 时月历单元格缩小，排期表横向滚动。

## 8. 权限与数据最小化矩阵

| 视图 | 数据范围 | 返回字段 | 校验点 |
| --- | --- | --- | --- |
| 个人月历、工作台“我的近期会议” | 我作为三类角色的项目 | 白名单字段 | 登录加路径权限规则 |
| 部门排期、工作台“本部门概览” | 调用人为部门负责人时，本部门（及下级，待决）成员 | 白名单字段加成员信息 | 服务端判定部门负责人身份 |
| 项目详情 | 现有规则不变 | 现有字段 | `requireProjectReadable` |

**已接受的风险**：部门负责人能知道非本人项目的存在、日期和负责人。需求已明确接受；缓解措施是字段白名单、接口不返回敏感字段，并在测试里断言响应体。

## 9. 异常与边界

- **会议日期为空（存量）**：不显示；页面提示“有 N 个项目未设置会议日期”，N 只统计我有权看的项目。
- **跨月、跨年的多日会议**：按区间重叠查询，前端逐日展开。
- **区间超限**：超过 62 天返回 400。
- **停用员工**：排期里保留并标“已停用”，具体见需求文档 8.6。
- **无部门归属的用户**：个人月历正常；部门负责人的范围不含他。
- **部门负责人本人**：排期里同样显示。
- **时区**：业务日期统一用 Asia/Shanghai，沿用 `DashboardReadService` 现有的时区常量。
- **取消、软删、恢复**：取消或软删后下次查询即消失，恢复后重新出现。
