# 审批界面「申请前后变化」对比 设计文档

> 项目：jshz-PMO 专家库子系统　版本：V1.0　日期：2026-10-26（实施 2026-10-27）
> 状态：已开发（随下次发布上线）　前置确认：交互 Demo 已用户确认无误

## 一、背景与问题

当前审批流中，审批人侧「审批管理」与申请人侧「我的申请」都只能看到申请人提交的**变更内容（新值）**，看不到变更前情况；根本原因是申请单只存新值 JSON，未保存旧值快照，审批通过后专家表已被更新，历史单无法还原变更前数据，照片类字段也无法对比。

## 二、改造目标

1. 审批人在「审批管理」打开**详情对比弹窗**，按字段并排查看「变更前 → 变更后」，照片新旧缩略图并排、可放大；
2. 通过 / 驳回整合进同一对比弹窗；
3. 申请人在「我的申请」只读查看对比；
4. 数据层为申请单新增 **oldData 旧值快照**。

## 三、方案设计

### 3.1 数据层（后端）

| 变更项 | 说明 |
|---|---|
| 旧值快照落位 | `application.biz_data.oldData`（JSON，中文键→旧值）。**注：需求原文写「expert_change_request 新增 old_data 字段」，实施时按已重构架构落位 biz_data 子键，零 DDL** |
| 提交修改申请 | `submitRequest` 提交时从 expert_info 读取专家当前全量字段（含照片文件名）写 `oldData` 快照（14 键：11 文本 + 3 照片） |
| 提交新增申请 | `submitCreateRequest` oldData 置空（无「变更前」） |
| 查询接口 | `/approval/requests`、`/approval/my-applications`（含 /my-requests）返回项增加 `oldData`（脱敏后）、`photoChanges`（照片原始文件名，供前端预览） |
| 照片处理 | oldData 照片存归档文件名走 `/api/files`；待审批新照片存临时目录走新增的 `/api/files-tmp` |
| 敏感脱敏 | oldData 中身份证号/银行卡号按查看者身份脱敏：管理员全量、非管理员前3后4（复用 `ExpertService.maskSensitive`，与 `/api/experts/{id}` 规则一致，不扩大可见范围） |

### 3.2 存量数据迁移（`database/migration/20261027_backfill_application_old_data.sql`）

| 申请单状态 | 处理方式 |
|---|---|
| `status=0` 待审批 / `status=2` 已驳回 / `status=3` 已撤回 | 用 expert_info 当前值回填 oldData |
| `status=1` 已通过 | 专家已更新、旧值丢失，保持空，前端提示「历史单无快照」 |

### 3.3 前端层

- 新增公共组件 `ApprovalDiffDialog.vue`（审批管理 + 我的申请共用）：Props `row` / `mode`（view/approve/reject），头部信息、申请原因、历史单提示条、字段对比表（字段 | 变更前 | → | 变更后）、按 mode 展示底部操作区。
- 展示规则：修改申请变更前=oldData[k]；新增申请（requestType=1）旧值列「-」+字段「新增」tag；照片字段新旧缩略图并排放大；历史已通过单（oldData 空）显示提示条。
- `ApprovalManage.vue`：列表操作列加「查看对比」（待审批/已处理均显示）；通过/驳回改打开对比弹窗对应 mode；摘要列升级「旧值 → 新值」；移除展开行实时查专家表逻辑。
- `MyApproval.vue`：操作列加「查看对比」（只读）；摘要列升级。

## 四、验收标准

1. 待审批/已处理/我的申请均可打开对比弹窗，文本字段正确显示旧值 → 新值；
2. 新增专家申请旧值列「-」，字段标「新增」；
3. 照片新旧缩略图并排、可放大；
4. 通过（意见可空）/ 驳回（意见必填）在弹窗内完成，操作后刷新；
5. 历史已通过单显示「历史单无快照」提示；
6. 我的申请可只读查看；
7. 存量迁移后待审批/已驳回/已撤回单对比正常，已通过单提示；
8. 新提交修改申请写入 oldData 快照；
9. 移除展开行逻辑后无报错。

## 五、涉及文件

**后端**：`entity/Application.java`（+oldData/photoChanges）、`service/ApplicationService.java`（快照写入/返回/脱敏/审批补强）、`config/WebConfig.java`（+/api/files-tmp）、`controller/ApplicationController.java`（listRequests 传 viewer）、`database/migration/20261027_backfill_application_old_data.sql`（新增）

## 六、与需求文档的映射差异（实施时核实）

需求文档基于旧架构（`expert_change_request` 表 / `change_data` 列 / `ApprovalService`），2026-10-26 已重构为通用申请主表 `application`（`biz_data` JSON 内含 `changes` 子对象）/ `ApplicationService` / `ApplicationController`，URL `/api/approval/*` 不变。本设计据此映射：

| 需求原文 | 实施落位 |
|---|---|
| `expert_change_request` 新增 `old_data` 字段 | `application.biz_data.oldData` 子键（零 DDL） |
| `change_data` 存新值 | `biz_data.changes` |
| `ApprovalService` / `ApprovalController` | `ApplicationService` / `ApplicationController` |
| 照片走 `/api/files/{filename}` | 旧照片走 `/api/files`；待审批新照片（TMP 临时目录不对外）新增 `/api/files-tmp` |

需求文档未覆盖、实施时核实发现的额外事实与决策：

1. **旧照片物理删除**：`approveModify` 原本通过后删除被替换的旧照片文件，会使 oldData 里的旧照片文件名 404。决策：oldData 快照存在时跳过删除，保证「任何时候都能还原变更前」；管理员直编/删除专家路径本次不动（已知限制：直编换照片仍会删旧文件，历史快照照片可能失效，前端降级为「已清理」占位）。
2. **临时照片不可读**：`/api/files` 仅映射正式照片库，待审批单新照片在临时目录无法预览，故新增 `/api/files-tmp` 映射（登录即可读，文件名随机不可枚举）。
3. **敏感字段可见范围**：原展开行 `GET /api/experts/{id}?sensitive=1` 仅管理员返回全量；本次 oldData 按同一脱敏规则返回，非管理员身份证/银行卡前3后4，不扩大可见范围。

## 七、约束与注意事项

- 遵循仓库 `AGENTS.md`：先核实现状、最小必要改动、文档同步铁律、高风险操作需负责人批准（回填脚本为生产数据 UPDATE，实施阶段仅编写+预演，实际执行在发布窗口经批准）。
- 照片字段 oldData 文件名读取走现有 `/api/files` 鉴权，不放开敏感字段权限。
- 不引入 WebSocket，实时性维持现有轮询/通知中心。
- 审批通过写入专家表时 `update_by` 语义保持现状（记申请人）。
