**改动点建议**
1. `FLOW_KEY` 单值 → 流程注册表驱动：`approval_config` 多行多值，按 `application_type` 映射 flowKey（EXPERT_MODIFY / EXPERT_CREATE / CONTRACT 等）；`findConfig()` 改为 `findConfigByFlowKey(String flowKey)`。
2. `getConfig()/updateConfig()` 增加 flowKey 参数；`updateConfig` 从"单行覆盖"改为"按 flowKey 更新指定行"。
3. `submitRequest/submitCreateRequest/submitContractApproval` 各自传入对应 flowKey；`checkSubmitEligible` 的启用判断改为按流程判断。
4. `getConfig()` 兜底自建行的默认 approverRole=ADMIN 改为按流程默认值（如新流程可默认 APPROVER）。
5. `approve/reject`：新增 status=4（退回修改）分支——退回时置 4、写 RETURN 记录、不清临时照片（区别于 reject 的 cleanTempPhotos）；重新提交时 status 4→0、写 RESUBMIT 记录。
6. `approve/reject` 增加或签判断：`extraApprover` 存在时任一操作即终态，否则维持待办。
7. `transfer/addApprover` 权限校验保持 `PERM_APPROVAL_AUDIT`，如需细分可新增 PERM 常量（注意同步 permission 表）。
8. `notifyApproverRole` 多流程下按流程配置的 approverRole 通知；若配置为具体审批人，改按 `approval_config_user` 通知。
9. 新增 `approval_config_user` 相关 Service 方法（按 configId 查/存具体审批人列表），复用 `assignableUsers()` 作为可选人数据源。

**权限风险提示（历史核查结论，改造须一并修复）**
- DbPermissionFilter 按 permission 表 type=2 `method+path→code` 校验。
- 线上 `role_permission` 缺 `approval:audit` 绑定（ADMIN 仅绑 approval:config+approval:manage；APPROVER 仅 approval:manage），存在 403 风险——本次新增审批端点前必须修复绑定。

`YYYYMMDD_<英文驼峰描述>.sql`，例：`20261022_add_approval_tables.sql`、`20261102_project_config_v2.sql`。约定：`USE expert_system;` 开头；幂等（CREATE TABLE IF NOT EXISTS / INSERT IGNORE / 条件 DELETE）；UTF-8 执行须走字节流重定向（历史踩坑：中文乱码，见 20261026_fix_b2_operation_log_utf8.sql）。

### 4.2 部署方式（蓝绿 / NSSM）

**服务现状（NSSM，<LOCAL_PATH>

| 服务 | 状态 | 端口/职责 | NSSM 参数 |
|---|---|---|---|
| ExpertSystemBackend | Running | 8080（生产） | `java -jar <LOCAL_PATH>`，AppDirectory <LOCAL_PATH> PID 2360（jdk-17.0.20.101-hotspot） |

**Nginx 配置**：模板 `<LOCAL_PATH>`，实际生效 `<LOCAL_PATH>`（80 → root <LOCAL_PATH> SPA；`/api/` 代理 127.0.0.1:8080，含 /api/health 同步切流注释；assets 缓存 30d）。

**发布顺序建议**：`build-all.ps1` → `deploy-backend.ps1`（蓝绿）→ `deploy-frontend.ps1`；或按运维体系设计文档顺序执行。
