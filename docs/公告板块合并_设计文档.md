# 公告板块合并 — 技术设计文档

- 版本：v1.0
- 日期：2026-10-30
- 项目：jshz-PMO 专家库系统
- 关联需求文档：`公告板块合并_需求文档.md`（ADR-01 ~ ADR-05 为本文设计依据）

---

## 1. 总体方案

将两个公告板块合并为**单页权限感知视图**：

```
个人中心 → 公告（唯一入口）
  ├─ 默认：阅读模式（ONLINE 列表 + 已读标记 + 置顶/过期标签）
  └─ 管理模式开关（canManage=true 可见）
        ├─ 全部状态 + 已读进度列 + 状态筛选
        └─ 管理工具栏：新建/编辑/删除/置顶/上下架/已读统计
```

- 删除 `/profile/announcements/manage` 路由与菜单，保留 `/profile/announcements`；
- `AnnouncementList.vue` 承担全部视图逻辑，管理弹窗（新建/编辑）以子组件形式按权限渲染；
- 后端**不改表、不改接口**，`GET /api/announcement` 的权限感知逻辑已天然满足单页需求；
- 仅需清理 `permission` 表 type=1 的公告管理菜单行（详见 §4.3）。

## 3. 前端设计

### 3.1 路由与菜单变更

**变更前（router/index.js，`/profile` 父级下）**：

```js
{ path: 'announcements', name: 'AnnouncementList', component: AnnouncementList, meta: { requiresAuth: true, title: '公告' } }
{ path: 'announcements/manage', name: 'AnnouncementManage', component: AnnouncementManage, meta: { requiresAuth: true, permissions: ['announcement:manage'], title: '公告管理' } }
```

**变更后**：删除 `AnnouncementManage` 路由项与对应组件引用；菜单树由 buildMenuTree 自动收敛为单个「公告」项。**同时全局检索 `AnnouncementManage` 字符串**（含菜单配置、常量、跳转引用），确保无残留死引用。

### 3.2 AnnouncementList.vue 改造

核心逻辑：

```js
const canManage = computed(() => authStore.hasPermission('announcement:manage'))
const manageMode = useLocalStorage('announcement_manage_mode', false) // 会话级记忆
const showManageBar = computed(() => canManage.value && manageMode.value)
```

- **模式开关**：`el-switch` 或按钮组，仅 `canManage` 渲染；关闭时恢复纯阅读布局。
- **列表渲染**：
  - 阅读模式：现有卡片/列表 + 置顶/过期标签 + 已读状态（复用现有代码路径）；
  - 管理模式：扩展列（状态、已读进度、操作列），操作列按钮受 `v-permission="'announcement:manage'"` 或 `showManageBar` 双重保护。
- **管理弹窗**：新建/编辑弹窗抽为 `AnnouncementFormDialog.vue`（可从 `AnnouncementManage.vue` 迁移复用），仅 `showManageBar` 时挂载。
- **详情页**：保持不变；管理模式入口同样跳转 `AnnouncementDetail.vue`（已含已读统计展示）。

> 踩坑提醒：合并视图后**模板绑定与保存取值必须同步迁移到同一响应式模型**，避免出现"界面提示成功、实际提交旧快照"的静默失败（参考历史：互斥弹窗合并时 v-model 绑定与 buildFormData 取值不一致的教训）。

### 3.3 已读/角标链路

`store\notification.js` 的 `loadAnnouncementUnread`、详情页已读上报接口保持不变，与合并无冲突。

## 4. 后端与权限模型设计

### 4.1 接口策略：零改动

| 接口 | 处置 |
|---|---|
| `GET /api/announcement`（分页，权限感知） | 保留，单页两种模式共用 |
| `GET /effective`、`/unread-count`、`/{id}`、`POST /{id}/read`、`POST /read-all` | 保留 |
| `POST /`、`PUT /{id}`、`DELETE /{id}`、`PUT /{id}/status`、`PUT /{id}/top`、`GET /{id}/read-stats` | 保留，`announcement:manage` 规则不动 |

### 4.2 权限码三层耦合点清单（全局检索范围）

`announcement:manage` 为跨层耦合概念，合并改造必须**同步核对以下全部落点**，任何一层遗漏会导致菜单异常或 403：

| 层 | 落点 | 处置 |
|---|---|---|
| ① 前端路由 meta | `router/index.js`（manage 路由删除后 meta 消失） | 删除 |
| ② 前端指令/逻辑 | `directives/permission.js`、`authStore.hasPermission` 引用点（AnnouncementList/Manage） | 收敛到单页 |
| ③ permission 表 type=1 | 公告管理菜单行 | 删除（见 4.3） |
| ④ permission 表 type=2 | 6 条管理接口规则 | 保留 |
| ⑤ DbPermissionFilter | method+path 匹配逻辑 | 不动 |
| ⑥ Service 兜底 | `AnnouncementService.requireManage` | 不动 |

> 踩坑提醒：DbPermissionFilter 按 method+path 命中即拦截，**改造必须"先删旧行、后（如需）插新行"**，只新增不删旧会导致命中旧规则 403。

### 4.3 数据库变更（仅 permission 表菜单行）

新增迁移脚本 `20261030_announcement_merge.sql`（**幂等，可重放**）：

```sql
-- 删除公告管理菜单行（type=1），接口规则（type=2）保留
DELETE FROM permission WHERE type = 1 AND code = 'announcement:manage' AND method IS NULL AND path LIKE '%announcement%manage%';

-- 校验：公告管理菜单行已清零
SELECT COUNT(*) AS leftover FROM permission WHERE type = 1 AND code = 'announcement:manage';
```

> 注意：删除前先在数据库确认该菜单行精确形态（permission 表 type=1 菜单行的 code/path 字段），避免误删其它行；执行后需重启后端使 PermissionService 缓存刷新。

### 4.4 越权脏数据核查（合并前置条件）

合并后管理能力暴露在普通公告页内，**必须先核查 `user_role` 是否有普通用户被误绑 `announcement:manage` 或 ADMIN 角色**，否则会出现越权暴露。核查 SQL：

```sql
-- 核查1：role_permission 中 announcement:manage 的绑定角色（应仅含 ADMIN 等预期角色）
SELECT rp.role_id, r.role_name, COUNT(*) AS bind_count
FROM role_permission rp JOIN role r ON r.id = rp.role_id
WHERE rp.permission_code = 'announcement:manage' OR rp.permission_id IN (SELECT id FROM permission WHERE code = 'announcement:manage')
GROUP BY rp.role_id, r.role_name;

-- 核查2：user_role 中是否存在绑定预期外角色的用户（如普通员工绑 ADMIN）
SELECT ur.user_id, u.username, ur.role_id, r.role_name
FROM user_role ur JOIN role r ON r.id = ur.role_id
JOIN user u ON u.id = ur.user_id
WHERE r.role_name NOT IN ('ADMIN', 'SUPER_ADMIN');
```

若发现脏数据，先按既定流程修正绑定，再执行合并上线的验收。

### 4.5 操作日志兼容

`OperationLogService` 的 6 个 ACTION 常量（`CREATE/UPDATE/DELETE/ONLINE/OFFLINE/TOP_ANNOUNCEMENT`）语义不变、代码不动，历史日志无需迁移。仅需在验收时确认新模式下的操作仍能正确写日志。

## 6. 验收与回归清单

### 6.1 功能验收

- [ ] 超管登录：菜单仅「公告」；默认阅读模式；可切管理模式；新建/编辑/删除/置顶/上下架/已读统计全部可用；
- [ ] ADMIN（绑定 `announcement:manage`）：行为同超管；
- [ ] 普通员工：仅「公告」菜单；无模式开关、无管理操作入口；阅读/已读/角标正常；
- [ ] 管理模式开关会话记忆（刷新不丢）；
- [ ] 编辑公告保存后，后端实际数据变更（避免静默旧快照坑）；
- [ ] 置顶、上下架、删除后列表即时刷新且权限数据正确。

### 6.2 安全验收（历史踩坑重点）

- [ ] 无权限直访旧路由 `/profile/announcements/manage` → 403/重定向；
- [ ] 无权限直调管理接口（POST/PUT/DELETE 等）→ 403；
- [ ] `role_permission` 中 `announcement:manage` 绑定仅含预期角色；
- [ ] `user_role` 无普通用户误绑 ADMIN/SUPER_ADMIN 脏数据；
- [ ] permission 表 type=1 公告管理菜单行已清零，type=2 接口规则 6 条完整保留；
- [ ] 操作日志：新模式下的新建/编辑/删除/上下架/置顶均写入对应 ACTION。

### 6.3 回归

- [ ] 首页/铃铛公告未读角标正常；
- [ ] 公告详情页（含已读统计视图）正常；
- [ ] 员工标记已读链路正常；
- [ ] 前端 `npm run build` 通过，Nginx 重启后线上生效。

## 7. 术语表（Glossary）

| 术语 | 含义 |
|---|---|
| 公告（阅读端） | 面向所有登录用户的公告浏览页，路由 `/profile/announcements` |
| 公告管理（管理端） | 面向管理员的公告维护页，路由 `/profile/announcements/manage`，本次合并删除 |
| `announcement:manage` | 公告管理权限码，跨前端路由 meta / permission 表 / DbPermissionFilter / Service 四层耦合 |
| canManage | 前端计算属性：当前用户是否持有 `announcement:manage` |
| 管理模式 | 公告单页内由权限持有者开启的视图，展示全部状态与管理工具栏 |
| SUPER_ADMIN | 超管角色，PermissionService 代码内强制全权，不依赖 role_permission 绑定 |
| DbPermissionFilter | 后端按 method+path 匹配 permission 表 type=2 规则的接口权限过滤器 |
