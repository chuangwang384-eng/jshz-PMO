## 1. 十项专项核查结果

### ① 已关闭/废弃端点

- **合规 V3→V4 切换后的旧写关闭**：旧个人写入口 `PUT /api/compliance/my-progress/{itemId}`、`PUT /api/compliance/my-reminder/{itemId}` 由 `rollout.requireV3(userId)` 守卫，用户切换 V4 后拒绝（V4 交接记录称"旧写 409"）。🥇 ComplianceService.java:649,689；ComplianceRolloutService.java:43；🥈 docs/handover/tasks/20261103_compliance_v4_release_blockers.md 第 4 节
- requireV3 守卫在当前代码中**仅这 2 处调用**；合规笔记本 `PUT /todos/{todoId}` 是项目合规待办（项目成员校验 + rowVersion 乐观锁），不属旧个人写。🥇 ComplianceNotebookService.java:315-329
- **兼容层端点仍在服役**（非关闭，而是旧路径兼容）：`GET /api/export/full|/md`（专家导出旧路径）、`GET /api/user/info`、`GET /api/approval/my-requests`（与 my-applications 一致）。🥇 ExportCompatController.java:39-65；UserInfoCompatController.java:27；ApplicationController.java:169-171
- 未发现用 `@Deprecated` 或 410 Gone 显式废弃的端点；"关闭"仅靠 V4 切换守卫实现。🥇（rg 全量枚举无命中）

### ② 长耗时操作的同步/异步

**四个 1-2 分钟级解析端点全部同步阻塞在请求线程**，用户无进度反馈、无法取消，且受 Nginx/浏览器超时约束：

| 端点 | 实现 | 证据 |
| --- | --- | --- |
| `POST /api/experts/resume/parse`（简历 OCR+LLM） | 同步调用 `resumeParseService.parse`：PDF/Word/图片→文本，扫描件回退 Tesseract OCR，再走本地 Ollama 语义抽取 | 🥇 ExpertController.java:103-115；ResumeParseService.java:39,90,188-195,285-287 |
| `POST /api/compliance/documents/{id}/reparse` | 同步 `complianceService.reparse`，仅以 409 挡重复触发（"文档正在执行上传解析"） | 🥇 ComplianceItemController.java:105-111；ComplianceService.java:243 |
| `POST .../template-workspace/extract`（模板抽取） | 同步 `sources.extract`（虽有 `extractions/latest` 轮询端点，extract 本身非 @Async） | 🥇 ComplianceTemplateWorkspaceController.java:35-36；ComplianceWorkspaceSourceService.java:29 |
| `POST /api/project/{id}/schedule/{scheduleId}/parse`（日程解析） | 同步 `scheduleParseService.parse` | 🥇 ProjectController.java:512-516 |

**已有的异步样板**：知识库解析 `KnowledgeParseTaskService` 用 `@Async("knowledgeParseExecutor")` + 独立线程池（KnowledgeAsyncConfig），解析状态在文档列表可见；企微同步经 `WecomSyncTrigger` 代理异步；抠图 PhotoMatteService 自管单线程池 + SLOT 限流。🥇 KnowledgeParseTaskService.java:56；WecomSyncTrigger.java:26；PhotoMatteService.java:36-53
→ 缺口本质：**异步能力已存在但未复用到其余三个解析场景**。Ollama 超时默认 180s（🥈 AGENTS.md 18.4），同步等待意味着最坏 3 分钟无响应。⚠️ Nginx 侧超时值未在本任务核实。

### ③ 审批流覆盖

- 审批流仅两个 flowKey：**EXPERT（专家新建/修改申请）与 CONTRACT（合同审批，通过后合同生效）**。🥇 ApplicationService.java:60-61；ApplicationController.java:94,111,126-128
- 审批操作完备：approve/reject/withdraw/transfer（转办）/add-approver（加签）/return（退回）/resubmit，均校验 `approval:audit`；审批人按 flowKey 快照配置。🥇 ApplicationController.java:211-292
- **关键缺口：专家模块存在绕过审批的直接写端点**。`POST /api/experts`（直接新建）、`PUT /api/experts/{id}`（直接修改）、`DELETE /api/experts/{id}`（直接删除）在 Service 层是 `save()/updateById()` 直写，不走任何审批流，且无权限码（见⑩）。🥇 ExpertController.java:185-239；ExpertService.java:136-146,182-197,249
- 无审批的操作（登录即可或仅权限码）：供应商增删改、客户增删改、知识库文档发布（仅 knowledge:maintain 权限码）、项目取消（PUT /{id}/cancel）、会议预算确认（POST /{id}/meeting-budget/confirm）、用户角色变更（直接改 + 通知）、合规事项确认/撤回。🥇 各 Controller 端点清单
- 通用审批引擎（flowKey 可扩展）已具备，但**除专家/合同外没有第三个流程接入**。🥇 ApprovalConfig 按 flowKey 存取，ApplicationService.java:129-178

### ④ 消息通知覆盖

### ⑥ 操作日志/审计覆盖

- 双轨：手动埋点（operationLogService.record / downloadAuditService）+ AOP 注解 `@OperationLog`（仅 SupplierController 6 处使用）。🥇 OperationLogAspect.java:31-37；SupplierController.java:147,158,170,251,282

### ⑦ 错误响应友好度（GlobalExceptionHandler）

- 覆盖：401 登录失败、403 权限不足、BusinessException、参数校验 400、类型转换 400、上传超限、唯一键冲突（友好提示+日志）、兜底 500（不泄露 SQL/堆栈）。🥇 GlobalExceptionHandler.java 全文
- 两个瑕疵：
  1. `handleBusiness` **无 @ResponseStatus** → 业务异常（如 409）HTTP 状态码为 200，仅 body.code 携带错误码；与 401/403/400 的真实 HTTP 状态不一致。🥇 GlobalExceptionHandler.java:42-45
  2. 上传超限提示**硬编码"单文件 ≤5MB"**，与 18.2 规定的可配置限额（expert.upload photo/resume/doc-max-bytes，经 /api/meta/limits 下发）脱节，配置改大后提示误导。🥇 GlobalExceptionHandler.java:77-80

## 2. 按业务域能力缺口表

### 认证权限
- 已有：账密+企微扫码登录、JWT、改密、RBAC 16 权限码、角色管理、权限点数据驱动、用户/角色 CRUD、登录态缓存清理。
- 缺：专家/供应商写操作权限码；用户软删/停用；密码策略/锁定；权限变更的审批。
- 影响：任何登录账号可改/删专家档案与供应商记录（有审计可查但无事前拦截）；离职用户只能硬删。

### 项目流程
- 已有：最重的模块（62 端点）——CRUD/软删恢复/阶段/取消/时间线/成员专家供应商文档/合同+审批生效/预算+报价版本/日程解析/演讲人归档/项目类型阶段模板配置。
- 缺：阶段变更/取消/成员变更**无通知**；取消/预算确认无审批；无项目统计聚合接口。
- 影响：项目动态只有当事人刷新页面才知道；预算确认一步生效无复核。

### 专家库
- 已有：列表/高级筛选/详情/简历 OCR+LLM 解析辅助/审批流申请（新建/修改）/6 种导出/导入/下载留痕。
- 缺：**直接写端点绕过审批且无权限码**；删除物理不可逆；简历解析同步阻塞 1-2 分钟；档案变更无通知；无版本化。
- 影响：核心资产完整性依赖自觉；误删无法恢复；解析期间前端长时间无反馈。

### 供应商
- 已有：CRUD/图片管理（≤20 张、≤8MB、累计 ≤100MB）/行价/评价/跨城绑定/字典管理（supplier:dict）/批量解绑/@OperationLog 审计（唯一 AOP 全覆盖的模块）/每小时图片清理。
- 缺：主 CRUD 无权限码；无导出导入；硬删无恢复；变更无通知。
- 影响：任何登录用户可删供应商（有引用保护）；数据整理只能逐条手改。

### 客户
- 已有：CRUD/软删恢复/附件/关系类型字典/关系网络/关系搜索目标。
- 缺：无导出导入；变更无通知；无统计。
- 影响：客户资料批量整理无工具支持。

### 知识库
- 已有：文档 CRUD/权限过滤列表/**异步解析**（唯一）/版本/下架上架/永久删除/收藏/文件预览。
- 缺：无导出；文档更新通知覆盖但无 RAG 问答集成；解析失败无重试任务。
- 影响：知识只能浏览不能问答（见 AI 助手域）。

### 合规
- 已有：V3+V4 双轨（V4 含执行/任务/事件/提醒/暂停恢复归档/复用/模板工作区/抽取/迁移）；V3→V4 切换守卫；笔记本待办（项目成员+乐观锁）；到期/提醒双调度。
- 缺：维护操作（reparse/withdraw/confirm）与 V4 执行操作**无操作日志**；无合规统计/导出。
- 影响：合规数据被谁改过查不到（页面行为可复现但无留痕）；完成率只能手算。

### 审批消息
- 已有：通用 flowKey 引擎（EXPERT/CONTRACT）、七种审批动作、转办加签退回重提、审批人快照配置、15 种通知类型、收件箱全套。
- 缺：**审批流只覆盖两个实体**；BusinessException HTTP 200；审批超时催办/自动提醒无。
- 影响：其余高危变更（预算、取消、供应商、角色）无审批通道；前端需按 body.code 判错。

### 工作台
- 已有：布局 v1/v2、快捷入口、聚焦页（focus/my-approvals/my-projects）、7 section 个人概览（MODULE_BUSY 保护）、全局搜索（模块可选）。
- 缺：管理侧聚合统计（专家库/项目/合规/知识库全局视图）。
- 影响：管理层无数据驾驶舱，只能导 Excel 自算。

### AI 助手
- 已有：/ask 关键词打分 + 本地 Ollama 意图选择（不可用自动降级）返回人工维护指引卡片；条目管理 ai:manage。
- 缺：**与知识库/AnythingLLM 割裂**——AnythingLLM（127.0.0.1:3001，Ollama qwen2.5:3b + LanceDB）已本机 Docker 部署但未接入 PMO 应用，中文知识库问答待验证；产品内无法对知识库内容提问。
- 影响：两个 AI 能力各自为战，用户感知"AI 问答"只覆盖操作指引。

### 运维接口
- 已有：/health /ready（版本/构建信息）、/api/meta/limits、存储 stats/孤儿扫描/清理（storage:manage）、企微手动同步+状态（wecom:sync）、审计查询（audit:view）。
- 缺：**存储 purge 等破坏性操作无操作日志**；无运行时配置查看/刷新端点。
- 影响：清理动作不留痕，出问题无法回溯是谁执行的。

## 3. Top 缺口（按用户价值排序）

1. **专家库直接写端点绕过审批 + 无权限码**（③⑩）——审批流形同虚设的旁路。
2. **四个长耗时解析全部同步阻塞**（②）——上传体验差，超时风险。
3. **项目/供应商/客户/专家变更零通知**（④）——协作靠刷新页面。
