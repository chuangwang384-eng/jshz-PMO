## 1. 全局结论

系统整体交互骨架是健康的：危险操作确认覆盖广（约 60 处 ElMessageBox.confirm）、列表页普遍有 v-loading + 分页、专家/项目/供应商/客户四个列表有三处做了 URL 状态回存、工作台（DashboardView）是全库体验标杆（分区错误态+重试、60s 自动刷新、Ctrl+K、键盘可调布局）。

但存在一条**贯穿性的硬伤**：全局 axios 超时 15s（`api/request.js:8`），而系统内有多条明示"需要 1-2 分钟"的同步长请求没有做超时覆盖——日程解析（上传与手动触发两条路径都会命中）、大文件导出、Office 预览转换。冷启动场景下这些操作**必然在前端超时失败**，且错误呈现为英文原文 toast 或被静默吞掉，后端实际仍在执行、结果无人告知。这是"用户走不通"级别的第一优先问题。

其余问题集中在：解析等待无进度反馈、错误态与空态混淆、小屏适配缺口、审批检索/打印等效率能力缺失。

## 2. 体验问题与机会表

分级说明：**A = 用户走不通（阻断或必现失败）**；**B = 走得通但痛苦（明显摩擦/误导）**；**C = 锦上添花（机会）**。

### A 类：用户走不通

| # | 页面/流程 | 问题 | 证据 | 置信 |
| --- | --- | --- | --- | --- |
| A1 | 项目详情 → 日程上传/解析（核心流程） | **冷启动下解析请求必超时**。① 前端全局 axios 超时 15s，`uploadSchedule`/`parseSchedule` 均无超时覆盖（`api/project.js:151`、`api/project.js:163-165`）；② 后端上传接口在请求线程内**同步**调用解析（`ScheduleParseService.java:150-160`，`parse(projectId, s.getId(), user)` 在 upload() 内直接执行）；③ 手动「开始解析」按钮同样调同步接口（`ProjectController.java:512-516`，`ScheduleParseService.java:275` 注释「触发解析（同步执行）」）；④ UI 自己明示耗时"本地大模型首次冷加载可能需要 1-2 分钟"（`views/project/ProjectDetail.vue:197`）。模型驻留 60 分钟（`OllamaService.java:268-270`），**冷启动或闲置超 60 分钟后**：上传日程 → 15s 超时 → 拦截器弹出英文原文 `timeout of 15000ms exceeded`（`api/request.js` 错误分支取 `error.message`），`onScheduleFile` catch 为空（`ProjectDetail.vue:1013-1028`）；点「开始解析」→ 15s 超时 → `doParse` catch 吞错后仅刷新状态，用户看到的按钮停止转圈、无任何结果说明（`ProjectDetail.vue:1051-1061`）。后端实际继续执行并完成，但**前端无轮询**（ProjectDetail 无 setInterval，对照 `MyApproval.vue:258` 有 30s 轮询），用户不知道要刷新页面才能看到候选。 | 确定（代码链完整；实际触发依赖冷启动条件，未运行时实测） |
| A2 | 专家库/项目管理 → 导出 | **大导出请求受 15s 超时约束**。`downloadFile` helper 用默认超时（`api/request.js` downloadFile 段，无 timeout 覆盖），全量含照片 ZIP（`api/expert.js` exportFullZip/exportEmployeeZip/exportSelectedZip）、项目导出 Excel（`views/project/ProjectList.vue:303-307`）全走此路径。专家量大 + 照片打包时大概率 15s 超时，表现为"导出成功"toast 前先弹网络错误且无文件落地。 | 高置信（代码确定；是否超时取决于数据量，未实测） |
| A3 | 知识星球/项目资料 → Office 文档预览 | **LibreOffice 转换请求受 15s 超时约束**。预览走"后端转换的 PDF 流"（`components/KnowledgeDocList.vue:161` 附近注释），`handlePreview`（`KnowledgeDocList.vue:482`）与 `openFilePreview`（`views/project/ProjectDetail.vue:1727`）所在文件均无 timeout 覆盖（全库仅 4 处覆盖：`api/dashboard.js`、`api/expert.js:87`、`ComplianceTemplateEditor.vue:261`、`MaintenanceBoard.vue:225`）。Office 冷启动转换超过 15s 时预览失败——有「预览失败，可下载查看」兜底（`KnowledgeDocList.vue:170`），但下载路径又回到 A2 的 15s 限制。 | 高置信推断（代码确定，冷启动耗时未实测） |

## 4. 待证项

1. **15s 超时的实际触发条件**：需在冷启动（后端刚起或 Ollama 驻留过期）实测上传日程/手动解析/全量 ZIP 导出/Office 预览的端到端耗时与前端表现。建议查法：重启后端后计时 `POST /api/project/{id}/schedule`。
2. **Nginx 代理超时**（`<LOCAL_PATH>` 的 proxy_read_timeout）：若小于后端实际耗时，会先于 axios 15s 产生 504；未读配置。
3. **小屏/平板真机表现**：代码层判断无 @media 即挤压，未在 768/1024/1366 宽度实测。
4. **上传后端在解析期间的事务与重复上传**：上传请求超时后用户重传，旧文件清理逻辑（`ScheduleParseService.upload` 硬删旧份）是否在并发重传下安全，未深查。
