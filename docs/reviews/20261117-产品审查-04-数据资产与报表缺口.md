## 1. 结论摘要

1. **数据资产厚、报表能力薄**：init.sql 共 86 张 CREATE TABLE（80 业务/结构 + 5 备份 + 1 schema_migration），覆盖项目/专家/供应商/客户/知识/合规/审批/企微 8 大域；但全后端**没有任何金额 SUM 聚合**（仅有的 3 处 `.sum()` 是存储字节数），管理层视角的六类数据支撑（财务汇总、专家参与度、供应商绩效与价格趋势、知识库使用、审批时效、合规敞口）**全部缺失**，其中 5 类"有数据无报表"、1 类（供应商价格趋势）连数据基础都不具备。
2. **现存"统计"全是个人或单点口径**：工作台是个人待办台（我的申请/待我审批/未读/我的项目风险），唯一的组织级统计界面是公告已读进度弹窗；下载次数仅维护人可见、专家下载次数甚至没有前端展示。
3. **暗数据与死资产**：2 张死表（`approval_template`、`expert_change_request`）零代码引用却仍在 init.sql 建表；2 个后端接口无前端消费（下载审计明细、专家下载次数）；5 张备份表进入新环境 bootstrap DDL 且绕过 parity 脚本过滤。
4. **数据质量有前科、有存量风险**：三个模块发生过演示/测试数据混入（客户 work_level 错录人物关系、客户关系表曾整表清空、项目/合规测试数据清理），其中 work_level 错录的清理决策是"界面自行清理、本期不动数据"，**当前是否已清待证**；软删四处堆积无归档策略；init.sql 表数口径自相矛盾（详见 §7）。

## 7. 治理发现：表数口径矛盾（文档同步铁律项）

1. **实测**：init.sql 86 张 CREATE TABLE = 80 业务/结构 + 5 备份（4×`*_customer_backup_20261029` + `wecom_migration_uk_username_backup`）+ 1 `schema_migration`。
2. **文件头自称**（init.sql:4）："纳入 85 张业务/结构表；排除 16 张历史备份/迁移标记表"；:14 又说"不含历史备份表（*_bak_*）"。85 = 86 − schema_migration，即**把 5 张备份表计入了业务口径**，且与"排除备份表"自相矛盾。
3. **传导**：docs/repo-map.md §2 写"85 业务表"，沿用该口径；AGENTS.md §0.5 生产口径 101=85+10+6。
4. **根因**：`scripts/check-schema-parity.ps1:68` 的过滤模式是 `*_bak_*` 或 `mig_*`——`*_customer_backup_20261029` 与 `*_username_backup` **都不匹配**，被当作业务表参与一致性校验。过滤盲区使该口径矛盾无法被脚本发现。
5. 另：repo-map 基线写 1.0.49（2026-11-17），实测 version.txt=1.0.50——地图版本号滞后一版。
