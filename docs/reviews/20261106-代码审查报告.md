## 2. 总体结论

系统功能完整、工程化程度较高（蓝绿发布、原子回滚、下载审计、操作日志、版本号单一真源、迁移脚本体系），基础安全设施（JWT + RBAC + 参数化 SQL + 路径穿越防护 + 富文本清洗）已经具备。

但当前存在**一组可串联的高风险问题**：

> 内网任意人员 → 用「同事姓名 + 111111」自动注册账号 → 以普通登录用户身份调用 `GET /api/experts` 获得全量专家**明文身份证号、银行卡号** → 还可通过未登记权限的 `GET /api/experts/selected/export` 导出全量明文表格。

这不是单点缺陷，而是「弱注册策略 + 接口默认放行 + 敏感字段无分级」三者叠加。**建议在下次发布前优先处理第 3 节 P0 项。**

风险分布：

| 级别 | 数量 | 说明 |
| --- | --- | --- |
| P0（发布阻断） | 3 | 可直接导致敏感个人信息批量泄露 |
| P1（高） | 7 | 越权、账号生命周期失效、权限模型 fail-open |
| P2（中） | 9 | 配置、性能、可维护性、可观测性 |
| P3（低/规范） | 5 | 文档漂移、残留文件、注释失准 |

## 3. P0：发布前必须处理

### P0-1 任意内网人员可用「姓名 + 111111」自动注册

**证据**
- `backend/.../service/AuthService.java:71`：查不到用户时直接进入 `autoRegisterAndLogin`。
- `AuthService.java:135-158`：只要姓名符合 `^[\u4e00-\u9fa5·]{2,20}$` 且密码为 `111111`，即创建 `is_admin=0`、`status=1` 的账号并绑定 `EMPLOYEE`。
- `application.yml`：`login-mode: ${AUTH_LOGIN_MODE:NAME}`，默认即 `NAME`（自动注册模式）。
- 初始密码固定为 `UserService.DEFAULT_PASSWORD = "111111"`。

**影响**
知道任意一位同事姓名即可注册/登录；系统无手机号、工号、邀请码或管理员审批校验，账号身份不可信。后续所有「登录即可」的接口都因此失去身份保证。

**建议**
1. 生产环境将 `AUTH_LOGIN_MODE` 切到 `MOBILE` 或 `COMPAT`，并关闭 `NAME` 自动注册分支（保留代码开关，不删除回滚能力）。
2. 自动注册增加第二因子（企微 userid、工号或管理员预置名单）。
3. 初始密码改为一次性随机口令或首次登录设置密码，禁止固定 `111111`。

### P0-2 专家身份证号/银行卡号对所有登录用户明文返回

**证据**
- `backend/.../controller/ExpertController.java:70`、`:86`：`boolean full = authUser != null;`——只要登录就按“完整字段”返回。
- `backend/.../service/ExpertService.java:196-203`：`toView(Expert, boolean full)` **完全忽略 `full` 参数**，直接返回原实体。
- 权限表未登记 `GET /api/experts`、`GET /api/experts/{id}` 规则，`DbPermissionFilter` 对未命中规则的请求直接放行。
- `README.md` 仍声明“身份证号/银行卡号查看页脱敏显示”，与实际实现不一致。

**影响**
脱敏只发生在界面展示层；任何登录用户（包括 P0-1 自动注册的账号）用浏览器 DevTools 或 `curl` 即可拿到全量明文 PII。这直接违反项目自身“最小必要访问”与个人信息保护要求。

**建议**
1. 列表接口默认脱敏（前 3 后 4），详情接口按 `expert:sensitive:view` 权限码返回明文。
2. 若业务确需“登录即可看明文”，至少补充**查看审计**（谁、何时、看了哪位专家的哪些字段）并在文档中明确风险与审批依据；当前只有下载留痕，没有查看留痕。
3. 修正 `README.md` 与 `docs/architecture.md` 的描述，避免安全预期失真。

---

### P0-3 勾选导出接口未登记权限，可绕过 `expert:export` 导出全量明文

**证据**
- `ExpertController.java:162` `GET /api/experts/selected/export`、`:178` `GET /api/experts/selected/zip`，均以 `full = true` 导出明文 Excel/照片 ZIP。
- 权限表仅登记了 `/api/experts/export`、`/api/experts/export/employee`、`/api/experts/export/full`、`/api/export/full`（`database/migration/20261022_add_rbac_tables.sql` 等）。
- 全库检索 `experts/selected` **无任何权限规则**。
- 已用本地 Spring `AntPathMatcher` 验证：`/api/experts/export` 不匹配 `/api/experts/selected/export`，确认不会被现有规则覆盖。

**影响**
任何登录用户传 `ids=1,2,3,...` 即可导出全量专家明文表格与三类照片，绕开 `expert:export` 的授权设计。下载审计会记录，但不能阻止泄露。

**建议**
1. 立即补充 `GET /api/experts/selected/export`、`GET /api/experts/selected/zip` 的 `expert:export` 规则（新增迁移脚本，遵循 R-3 向后兼容）。
2. 将导出权限进一步拆分为 `expert:export:sensitive`，与普通导出分离。
3. 导出前校验 `ids` 数量上限，避免一次性拖库。

## 4. P1：高优先级

### P1-1 RBAC 管理接口可纵向提权

**证据**
- `controller/UserController.java:105` `PUT /api/users/{id}/roles` → `UserService.assignRoles`，仅校验角色存在且启用，**未禁止分配 `SUPER_ADMIN`**。
- `RoleController.assignPermissions` 仅禁止修改 `SUPER_ADMIN` 角色自身绑定，**未限制“不能授予自己未拥有的权限码”**。
- `UserService.assignRoles` 使用“先删后插”覆盖式分配，且未校验操作者与目标用户的关系。

**影响**
持有 `user:manage` 的账号可把自己或他人提升为 `SUPER_ADMIN`（`PermissionService` 对 `SUPER_ADMIN` 代码内强制全权）；持有 `role:manage` 的账号可给自己的角色追加任意权限码。等于 RBAC 管理员可无限制提权。

**建议**
1. 分配 `SUPER_ADMIN` 仅允许当前 `SUPER_ADMIN` 执行，且禁止自我提权/降权最后一名超管。
2. 授予权限码必须是操作者权限集合的子集（防越权授予）。
3. 关键角色变更增加二次确认与独立审计（现有 `operation_log` 保留）。

### P1-2 账号停用/删除后 Token 仍可用最长 8 小时

**证据**
- `security/JwtAuthenticationFilter.java`：仅解析 JWT 与角色，**不查询 `sys_user.status`、不校验用户是否存在**。
- `security/AuthUser.java`：`isEnabled()` 恒返回 `true`，`isAccountNonLocked()` 恒 `true`。
- `JwtTokenProvider`：`expire-hours: 8`，无 token 版本号/黑名单/吊销机制。
- `UserService.updateUser`（停用）与 `deleteUser` 均未清理权限缓存，也未使已签发 token 失效。

**影响**
管理员停用或删除账号后，当事人仍可继续访问系统最长 8 小时；若权限缓存未清，角色变更也可能延迟生效。

**建议**
1. JWT 增加 `tokenVersion`（或 `pwdChangedAt`）claim，用户表增加对应字段；过滤器比对不一致即拒绝。
2. 过滤器对用户状态做**短 TTL 缓存校验**（如 60 秒），停用后最迟 1 分钟失效。
3. 停用/删除/改密/改角色时递增 `tokenVersion` 并清理缓存。
4. `AuthUser.isEnabled()` 返回真实状态，避免安全框架误判。

### P1-3 强制改密只有前端约束

**证据**
- `mustChangePassword` 仅出现在 `AuthUser`、`JwtTokenProvider`、`LoginResponse`，**全后端无任何拦截逻辑**。
- `SecurityConfig` 未配置“未改密只能访问 `/api/auth/**`”的规则；`DbPermissionFilter` 也不检查该标记。
- 前端 `router` 跳转可被绕过（直接调用接口）。

**影响**
初始密码 `111111`（或管理员重置后）可长期不变直接使用全部功能，与“初始密码强制改密”的安全设计不符。

**建议**
在 `JwtAuthenticationFilter` 之后增加 `MustChangePasswordFilter`：`mustChangePassword=true` 时仅放行 `/api/auth/me`、`/api/auth/change-password`、`/api/auth/logout`，其余返回 403（带明确错误码）。

### P1-4 接口权限模型 fail-open，且规则匹配“首条命中即止”

**证据**
- `security/DbPermissionFilter.java:44-63`：遍历规则，命中第一条即 `break`；未命中任何规则直接 `chain.doFilter` 放行。
- `PermissionService.getPermissionRules()`：`selectList` **无 `orderBy`**，多条通配规则重叠时匹配顺序不确定。
- 现状：252 个接口映射 vs 约 125 条接口权限规则（静态统计），大量接口依赖“登录即可”或业务层零散校验。

**影响**
1. 新增接口若忘记登记权限，默认对所有登录用户开放，且不会有任何告警。
2. 两条规则同时匹配同一路径且权限码不同时，实际生效规则取决于数据库返回顺序，存在不可预期行为。
3. 维护成本高：授权分散在“SQL 种子数据 + 代码内 `hasPermission`”，容易出现口径不一致。

**建议**
1. 改为**默认拒绝**：未登记规则的 `/api/**` 返回 403，白名单（登录、健康检查、本人信息等）显式声明。
2. 规则加载时按 `path` 长度/精确度排序（精确 > 单段通配 > 双段通配），或在启动时检测重叠规则并报错。
3. 增加启动自检：扫描所有 `@RequestMapping`，对未登记权限的接口输出 WARN 清单。
4. 逐步用 `@PreAuthorize("hasAuthority('xxx')")` 替代零散的业务层判断，便于审计。

### P1-5 知识文档下载不校验上下架状态

**证据**
- `controller/KnowledgeController.java:216` `GET /api/knowledge/docs/files/{fileName}`：仅 `resolveDocument` 校验路径，**未校验文档 `status`，也未校验当前用户是否维护人**。
- 注释明确“登录即可”；下架（status=0）只影响列表展示。

**影响**
已下架的敏感文档，只要知道/猜到文件名（`doc_<时间戳>_<原文件名>`）仍可下载；文档撤权后旧链接继续有效。

**建议**
下载前按 `fileName` 反查文档，校验 `status=1` 或当前用户具备 `knowledge:maintain`；下架/删除后同步失效下载链接。

### P1-6 照片与身份证影像仅“登录即可”访问，无权限分级与查看审计

**证据**
- `config/WebConfig.java:36`、`:47`：`/api/files/**` 映射正式照片库，`/api/files-tmp/**` 映射审批临时照片库；均为静态资源，仅受 `authenticated()` 保护。
- 文件命名规则可预测：`avatar_<expertId>_<epochMillis>`、`idcard_front_<expertId>_<epochMillis>`（`PhotoStorageService`）。
- 无 `download_log`/`operation_log` 记录照片查看行为。

**影响**
任意登录用户拿到 URL 即可查看他人身份证正反面、证件照；临时目录审批中照片同样可读。缺少查看留痕，泄露后难以追溯。

**建议**
1. 改为受控下载端点（如 `/api/experts/{id}/photo?type=`），按 `expert:sensitive:view` 或本人/审批人校验。
2. 关闭 `/api/files-tmp/**` 的直接静态映射，审批预览走带权限的接口。
3. 记录敏感影像查看审计（人、时间、专家、类型、IP）。

### P1-7 全局异常把内部异常信息返回给客户端

**证据**
- `config/GlobalExceptionHandler.java:73`：`ApiResponse.error(500, "服务器内部错误：" + e.getMessage())`。

**影响**
SQL 异常、文件路径、类名、依赖内部信息可能直接暴露给前端；也便于攻击者探测实现细节。

**建议**
对外统一返回“服务器内部错误 + 请求 ID”，详细堆栈只写服务端日志；日志中同时避免打印 PII（见 P2-5）。

## 5. P2：中等优先级

### P2-1 登录无失败次数限制、无锁定、无失败审计
`AuthService.login` 仅做 BCrypt 比对，未见失败计数、验证码、IP 限流或锁定；默认密码固定为 6 位数字（`111111`）。在 P0-1 场景下暴力/撞库成本极低。建议增加失败计数（账号 + IP 双维度）、指数退避、失败登录写 `operation_log`。

### P2-2 密码策略偏弱
`AuthService.changePassword` 仅要求长度 ≥ 6，无复杂度、无历史密码、无默认密码黑名单。建议至少 8 位 + 字母数字组合，并禁止 `111111`、姓名、手机号等弱口令。

### P2-3 部署配置与“仅内网”约束不完全一致
- `application.yml`：`server.address: 0.0.0.0`，而文件注释与 README 均写“仅监听内网地址”。
- 所有存储目录硬编码 `<LOCAL_PATH>`（照片、知识库、项目、客户、供应商），换机/迁移必须改代码配置。
- `SecurityConfig` CORS 允许 `localhost:5173`、`<PRIVATE_IP>:5173` 等开发来源，生产环境建议只保留正式域名。
- Cookie `secure=false`（内网 http 的客观限制），但需在文档中明确“禁止将该服务暴露到公网/HTTPS 代理未启用时风险”。

建议：`server.address` 改为可配置项（默认内网 IP），存储根目录统一由 `APP_STORAGE_ROOT` 注入，CORS 来源按环境变量配置，并在部署文档中写明防火墙要求。

### P2-4 无 Token 吊销/刷新机制
固定 8 小时有效期，无刷新令牌、无“退出所有设备”、无密码变更后强制下线。与 P1-2 同源，建议一并引入 `tokenVersion`。

### P2-5 日志与异常中的敏感信息边界需复核
`GlobalExceptionHandler` 打印完整堆栈，业务层多处 `BusinessException` 直接拼接 `e.getMessage()`（如 `PhotoStorageService` 保存失败）。建议统一异常脱敏规范，禁止在日志/响应中出现身份证号、银行卡号、完整简历内容。

### P2-6 项目列表存在 N+1 查询
`ProjectService.toBriefMap`（`ProjectService.java:175-186`）对每一行调用：
- `configuration.snapshot(projectId)`（配置快照查询）
- `usernameOf(ownerId)` / `usernameOf(creatorId)`（各一次 `selectById`，`:1728`）
- `executorNamesOf` / `executorIdsOf`（各一次查询，`:1691`、`:1698`）
20 条列表约产生 60-100 次 SQL。建议批量查询用户与执行人后内存组装，或将常用字段冗余到项目表。

### P2-7 大文件上传存在内存与阻塞风险
`KnowledgeController.update` 中 `file.getBytes()` 将最大 50MB 文档整体读入堆内存，随后同步触发解析/OCR；`KnowledgeDocTextExtractor`、`DocPreviewService` 的转换也是同步调用。并发上传/预览时可能造成堆压力与请求线程长时间占用。建议流式落盘、解析改为异步任务并记录任务状态。

### P2-8 关键写操作缺少事务或异常处理不当
- `UserService.assignRoles`：`delete` + 循环 `insert` 多写操作**未标注 `@Transactional`**，中途失败会留下“角色被清空”的中间状态。
- `UserService.deleteUser` 仅删除 `sys_user`，未清理 `user_role`、通知、收藏等关联记录，存在孤儿数据。
- `KnowledgeController.update` 中文档更新成功后调用合规解析，`catch (Exception ex) {}` **空捕获**，失败无日志、无告警，问题不可观测。

### P2-9 依赖版本偏旧（需结合安全公告核实）
`spring-boot-starter-parent 3.2.5`、`jjwt 0.11.5`、`pdfbox 2.0.31`、`jsoup 1.17.2` 均为较旧版本。**本次未联网核对 CVE，不能断言存在已知漏洞**；建议在下个维护窗口执行依赖扫描（如 `mvn dependency-check` / `npm audit`），并制定升级计划。

## 6. P3：低风险与工程规范

1. **文档与实现漂移**：`README.md` 写“后端 Controller 18 个”，实际 26 个；写“身份证/银行卡脱敏显示”，实际接口返回明文；`UploadController` 注释写“仅 ADMIN”，实际由 `upload:manage` 控制。违反 `AGENTS.md` 第 0 节“文档同步铁律”。
2. **前端巨型组件**：`ExpertList.vue` 1322 行、`ProjectDetail.vue` 1168 行、`SupplierDetail.vue` 900 行、`StepWizard.vue` 720 行，单文件承担数据加载、权限判断、表单、弹窗与样式，回归成本高。建议按“列表 / 详情 / 表单 / 弹窗”拆分，逻辑抽到 composable。
