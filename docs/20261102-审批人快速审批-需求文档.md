## 1. 背景与问题

### 1.1 业务背景

jshz-PMO 专家库子系统存在三类申请单（专家新增 EXPERT_CREATE / 专家信息修改 EXPERT_MODIFY / 合同 CONTRACT），由管理员与审批角色（APPROVER）持有 `approval:audit` 权限进行审批。当审批人待办堆积较多时，需逐条打开对比弹窗处理，处理效率低、易积压。

### 1.2 现状事实（file-agent 只读核查产出）

| 编号 | 现状事实 | 证据 | 影响 |
|---|---|---|---|
| F1 | 无批量操作：待审批列表无全选/批量通过/批量驳回，每单必须逐条打开对比弹窗处理 | `frontend\src\views\ApprovalManage.vue`；`ApplicationService.java` 无批量接口 | 堆积时逐条点击，效率低 |
| F2 | 驳回强制填写意见，通过/驳回均需弹窗确认 | `ApplicationService.java:590-591` | 逐单交互成本高 |
| F3 | 待办列表≠可审批集合：列表不过滤 `current_assignee`，转办后的单仍显示在他人待办列表，点击后才被后端拦截 | `ApplicationService.java:330-344` + `checkAssignee` L807-815 | 出现「看得见审不了」的无效条目 |
| F4 | 多审批人共享同一批待办，无认领/分配机制，可重复处理 | `listRequests` 全员可见 | 重复劳动与冲突 |
| F5 | 列表筛选维度少：仅 status + keyword，无类型/时间范围/紧急度 | `ApplicationService.java:330-344` | 堆积后无法快速聚焦 |
| F6 | 通知非实时：站内信 + 30s 轮询，无实时推送与超时提醒，通知失败静默 | `store\notification.js:27` | 待办到达感知滞后 |
| F7 | 已处理页按多状态统一分页，可回查审批历史 | `ApprovalManage.vue:175-185`；`approval_record` 表 | 支持追溯 |
| F8 | 权限三方一致（前端 v-permission / 后端 hasPermission / RBAC SQL），20261031 已修复转办加签越权 | RBAC SQL + 迁移脚本 | 权限无阻塞，改造安全 |

### 1.3 外部产品模式调研

| 产品/方案 | 快速审批模式要点 |
|---|---|
| 钉钉 OA 审批中心 | 待办中心集中处理 + 批量同意/拒绝审批任务接口 + 分来源筛选 + 流程交接（批量转交待办） |
| 钉钉消息卡片一键审批 | 三方系统审批同步钉钉待办中心，卡片上一键通过/拒绝，无需跳转 |
| 钉钉流转规则 | 超时自动处理、超时催办（12h 未处理二次提醒）、节点催办 |
| 企业微信/三方集成 | Webhook 卡片消息一键通过/拒绝、离线提醒升级、个人审批统计 |
| 通用设计规范 | 批量操作事务原子性 + 部分成功明细返回；批量适合高频低风险，高风险逐条；审批记录留痕；多筛选维度 |

## 2. 需求必要性评估

**结论：必要，但应控制边界，避免过度设计。**

- **支撑依据（内部）**：F1 无批量、F3 待办不隔离、F4 重复处理、F5 筛选单一，直接命中「堆积时效率低」的核心痛点。
- **支撑依据（外部）**：钉钉/企业微信等主流产品均以「批量操作 + 待办隔离 + 筛选聚焦 + 提醒催办」作为快速审批的标准能力组合，说明该需求方向成熟、风险低。
- **边界控制**：jshz-PMO 仅三类申请，审批量为中等（20-100 单/周），因此本期聚焦「看得到、批量审」的最小高价值闭环（待办隔离 + 批量通过/驳回 + 筛选增强），提醒催办、统计看板、实时推送等列入非本期范围，避免过度设计。

## 3. 目标用户与场景

- **目标用户**：管理员（ADMIN）、审批角色（APPROVER），均持 `approval:audit` 权限。
- **典型场景**：审批人收到多条待审批通知后，进入审批管理页，勾选同一类型或相近时间段的单据批量通过；对不符合条件的单据批量驳回并填写公共意见。
- **量级假设**：周审批量 20-100 单；峰值时待办可积压数十单。

## 5. 功能需求

### FR1 我的待办隔离

- 待审批列表（status=0）过滤条件为以下三者并集：
  1. `current_assignee` 为空（共享池，任何审批人可审）；
  2. `current_assignee` = 当前登录用户（被转办给我的）；
  3. `extra_approver` = 当前登录用户（被加签给我的）。
- 后端在 `listRequests()` 增加按当前用户过滤，前端无需感知过滤逻辑，仅展示「我的待办」。
- 交互：无「看得见审不了」的条目；点击审批仍保留 `checkAssignee` 后端兜底校验（并发/越权防护）。

### FR2 批量通过

- 支持对勾选的 N 张待审批单（status=0 且属于当前用户可审集合）批量执行通过。
- 通过前强制二次确认（弹窗展示所选数量、类型分布）。
- 处理语义与单条 `approve()` 一致：按申请类型分派 `approveCreate / approveContract / approveModify` 对应业务逻辑。
- 批量结果支持**部分成功**：逐条校验，成功/失败分别返回，失败项附失败原因（如已被处理、转办/加签归属不符）。

### FR3 批量驳回

- 支持对勾选的 N 张待审批单批量驳回。
- **公共意见必填**，限 200 字，应用到全部所选单据，逐条写入审批记录 comment。
- 驳回后清理临时照片（沿用单条驳回逻辑）。
- 批量结果支持**部分成功**，规则同 FR2。

### FR4 列表筛选增强

- 在现有 status + keyword 基础上增加：
  - **申请类型多选**：EXPERT_CREATE / EXPERT_MODIFY / CONTRACT；
  - **提交时间范围**：起止日期，按 `create_time` 过滤。
- 筛选条件与「我的待办」过滤条件可叠加使用。

### FR5 批量交互与二次确认

- 审批管理页（待审批 Tab）列表增加复选框列。
- 顶栏提供「批量通过」「批量驳回」按钮，未勾选时禁用。
- 二次确认弹窗：展示所选数量、类型分布；批量驳回时在弹窗内填写公共意见。
- 批量提交后展示结果：成功数量、失败明细（单据标题 + 失败原因），失败项保留在待办列表。

## 6. 非功能需求

| 维度 | 要求 |
|---|---|
| 权限 | 批量通过/驳回沿用 `approval:audit`，不新增权限点；前后端 + RBAC 三方一致 |
| 事务 | 批量接口采用整体事务 + 逐条校验，任一单据业务校验失败仅影响该条，不整批回滚；返回部分成功明细 |
| 防重 | 沿用 `getPending()` 乐观防重，避免并发重复审批；批量内同单不重复处理 |
| 留痕 | 每条单据单独写一条 `approval_record`（node_name 标注「批量审批」），可追溯至操作人/时间/意见 |
| 通知 | 批量通过/驳回后逐条给申请人发送 `TYPE_APPROVAL_RESULT` 站内通知（沿用现有机制） |
| 性能 | 单次批量上限建议 50 条；接口响应在常规列表量级下无显著劣化 |
| 兼容 | 前端页面为整页 `v-permission="'approval:audit'"`，改造不改变路由与权限入口 |

## 8. 验收标准

1. 审批人登录后，待审批列表仅显示本人可审的单据（共享池 ∪ 转办 ∪ 加签），不再出现「看得见审不了」的条目。
2. 勾选多张单据可批量通过；二次确认弹窗正确展示数量与类型分布；操作后单据状态置为已通过，申请人收到结果通知。
3. 勾选多张单据可批量驳回；公共意见必填且限 200 字；操作后单据置为已驳回，临时照片被清理，申请人收到结果通知。
4. 批量操作含已被他人处理的单据时，返回部分成功明细，失败项原因明确且保留在待办列表。
5. 列表可按申请类型多选、提交时间范围筛选，并与我的待办过滤叠加生效。
6. 权限校验：无 `approval:audit` 的用户不可见入口、不可调用批量接口；转办/加签归属不符的单据即使被勾选也会在批量中返回失败。
7. 每条批量操作在 `approval_record` 中逐条留痕，node_name 为「批量审批」，comment 为公共意见。
