# 项目开发流程规范（项目必读）

> 适用范围：jshz-PMO 景帅会展内部管理系统（专家库/会议管理方向）
> 维护：项目负责人 王创 | 生效日期：2026-10-30

---

## 一、核心纪律：完成一个功能即提交

**硬性要求**：每完成一个功能模块（判定标准见下），必须**立即 commit**，禁止把多个模块的改动长期堆积在工作区。

### 1.1 功能完成的判定标准（缺一不可）

1. **数据库迁移已落库**：`database/migration/` 下对应 SQL 已存在且已在目标库执行；
2. **前后端可用**：后端接口可调用、前端页面可操作，无编译错误、无启动失败；
3. **自测通过**：主流程（增删改查/审批/同步等）手工或脚本验证通过；
4. **验收确认**：按第四节流程完成部署与验收（见"部署上线-验收-修改-提交"）。

### 1.2 Commit Message 规范

统一格式（前缀必带）：

```
<模块名>-<日期>: <本次改动一句话描述>

示例：
企微通讯录同步-20261030: 企微通讯录同步与账号体系改造（三模式登录、部门填充、同步管理）
消息中心合并-20261030: 单铃铛右侧抽屉消息中心（全部/系统消息/公告，unread-count/read-all）
项目管理-20261030: 项目管理模块全套与合同审批（实体/Mapper/Service/Controller、页面、路由菜单）
```

### 1.3 跨模块联动的提交顺序

存在依赖关系时，**先提交被依赖方，再提交依赖方**：

- 被依赖方（先提交）：基础配置、用户/权限体系、公共组件、数据库基线；
- 依赖方（后提交）：业务功能模块（企微同步、项目管理、客户管理、供应商等）。

典型顺序：系统配置/数据库基线 → 用户及权限体系 → 企微同步 → 消息中心 → 项目管理 → 客户管理 → 供应商 → 知识库/专家库。

## 二、完整开发流程（一步都不能少）

```
需求梳理 → 设计评审 → 开发实现 → 本地自测 → 数据库迁移落库
→ 部署上线 → 上线验收 → 修改完善 → 立即提交（commit）→ 记录交接
```

每个环节都必须走完，禁止跳过中间步骤直接进入下一环节。

| 环节 | 要求 |
|------|------|
| 需求梳理 | 明确需求来源、验收标准、影响范围，写入 `docs/` 需求文档 |
| 设计评审 | 关键模块出设计文档（表结构、接口、页面、部署影响） |
| 开发实现 | 前后端按模块推进，保持工作区可编译 |
| 本地自测 | 主流程验证通过；审批/权限/异常分支覆盖 |
| 数据库迁移落库 | migration SQL 命名 `YYYYMMDD_模块_描述.sql`，并在目标库执行 |
| 部署上线 | 按 `scripts/deploy-frontend.ps1` 及后端部署规范执行（Nginx + NSSM） |
| 上线验收 | 部署后必须逐项验收（功能、权限、页面、日志），发现问题立即记录 |
| 修改完善 | 验收问题修复后重新部署，直至验收通过 |
| 立即提交 | 验收通过后按 §1.2 规范 commit，工作区不积压 |
| 记录交接 | 关键改动写交接文档（docs/handover-*），供后续维护 |

---

## 三、工作区管理红线（禁止事项）

1. 禁止 `git reset --hard` / `git clean -fd` / `git checkout .` / `git stash pop` 等一次性撤销动作；
2. 禁止未经确认删除或覆盖他人/历史代码；
3. 禁止用通配符批量删除/修改后不核对影响面；
4. 禁止把多个模块混在一个 commit 提交（特殊情况需在 message 中标注联动关系）；
5. 禁止长期（超过一个工作日）保留未提交改动。

---

## 四、部署上线-验收-修改-提交 全流程细则

### 4.1 部署上线
- 后端：编译产物部署至 NSSM 服务目录，重启服务并确认健康检查通过；
- 前端：执行 `scripts/deploy-frontend.ps1` 构建并发布至 Nginx 站点目录；
- 数据库：按顺序执行新增 migration，核对执行结果无报错。

### 4.2 上线验收
- 功能验收：本模块主流程 + 关键分支逐项点击验证；
- 权限验收：管理员/员工/审批人等角色分别验证权限边界；
- 回归验收：与本模块联动的既有功能抽查（被依赖方不回归）。

### 4.3 修改完善
- 验收发现的问题立即记录（现象/复现步骤/影响），修复后重新部署并复验；
- 验收不通过前，不执行"提交"环节。

### 4.4 提交
- 验收通过后立即按 §1.2 规范 commit；
- 跨模块联动时按 §1.3 顺序提交；
- 提交后 `git status` 确认工作区干净，无遗留未提交改动。
