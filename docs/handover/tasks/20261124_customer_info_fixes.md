## 变更及接口

- `PUT /api/customer/{id}` 将显式提交的空字符串或纯空白写入 SQL NULL，适用于单位、职位、职级、现任职务、喜好、备注。省略字段或传 JSON null 延续原来的保留行为。响应重新读取已保存档案。
- `GET /api/customer` 的 relationCount 只统计两端有效的关系。软删除期间关系记录仍保留，恢复后重新计入。已删除客户的抽屉提供只读摘要和恢复入口，正常客户的抽屉按 ID 识别人，并忽略其他打开会话的关系响应。
- `GET /api/customer/relations/search-targets` 在传 customerId 时排除当前客户，允许选到已有其他关系的客户。同类型关系仍在创建时按方向判重。新建档案弹窗的已选目标提示沿用既有规则。
- 新增登录后可读的 `GET /api/customer/limits`，返回 nameMaxLength（100）和 createRelationLimit（10）。三个姓名输入共用后端限额。新增客户附带关系最多 10 条，后端在插入前校验。打开新增弹窗遇到限额读取失败时仍可保存基本资料。
- 全局图上限仍为 500 位，只在实际超限时返回 truncated。保留前端布局尺寸、分页大小和其他输入长度作为既有界面约束。清理两处未使用的箭头函数、列表新增弹窗的编辑分支、详情页编辑弹窗的新增标题和未使用的删除状态。
- 写操作沿用 customer:manage。数据库结构、权限数据、环境配置和依赖无变更，无迁移。应用前后端应配套发布，后端先提供限额接口。

## 业务验收与回滚

1. 使用隔离环境的维护账号，在快速编辑和完整档案页清空已有喜好或备注，保存后刷新并重新打开。再修改有文本的字段，确认保存及展示一致。
2. 创建两份同名客户及不同关系，快速切换抽屉，确认关联人物和当前档案匹配。删除其中一个关联对象，确认对方关系列和关系图都隐藏该连线。打开回收站确认能看摘要、恢复且无无效入口。恢复后核对关系重新呈现。
3. 给已有「同事」关系的两位客户添加另一种有效关系，确认能搜索选人、原关系保留、相同类型和方向的重复提交得到已有关系提示。使用普通账号确认只能读取有效档案，维护操作仍按原授权拒绝。
4. 在测试环境验证姓名 100 和 101 字、一次关联 10 和 11 条，以及全局图 500 和 501 位客户的边界。
5. 下一步以当前分支运行以上隔离验收。生产发布需项目负责人批准。回滚时配套恢复前后端版本。若业务已经成功清空字段，应用版本回滚不会恢复原字段值。
