## ADR-001：文本保存报错修复策略 —— 全量加固 vs 单点修复

**状态**：已接受

**背景**：`saveRichText` 因前端未传 `templateId`，后端 `Long.valueOf(String.valueOf(null))` 抛出 NumberFormatException；代码扫描发现全后端共 9 处同型 `Long.valueOf(String.valueOf(...))` 模式，均为潜在同类缺陷。

**选项**：
- a) 单点修复：只修 `saveRichText` 一处 + 前端补传 templateId；
- b) 全量加固：抽取 `ParamUtils.parseLong` 安全解析工具，替换全部 9 处（选定）。

**决策**：选择 b。

**理由**：
1. 同型缺陷一旦再现即为线上事故，一次修干净成本最低（工具方法 + 机械替换）；
2. `ParamUtils` 本就是公共工具类，符合职责归属；
3. 前端补传 templateId 作为第一道防线，形成纵深防御。

**后果**：9 处行为需回归；缺参语义由各业务点自行决定（默认值或明确业务异常），不再产生 500 级未捕获异常。

## ADR-002：回退权限模型 —— 独立 canRollback 字段

**状态**：已接受

**背景**：现状前端回退按钮复用 `detail.canAdvance && hasPrevPhase`，推进与回退共用同一权限标记（`isOwnerOrExecutor`）。

**决策**：后端详情接口新增独立字段 `canRollback = isOwnerOrExecutor(project, user)`，前端回退按钮显隐改由 `canRollback` 控制。

**理由**：
1. 推进与回退是语义不同的业务动作，权限解耦后未来可分别调整（如回退收紧到负责人、或放开到创建人）；
2. 本次实现上 canRollback 与 canAdvance 取值相同，但**契约独立**，避免将来误伤一方；
3. 同时满足需求「回退权限放开给执行人」——实现上 `isOwnerOrExecutor` 已包含 `project_executor` 表中的执行人，无需新增数据模型。

**后果**：前端仅一处条件表达式变更；后端 getDetail 新增一个返回字段，兼容旧客户端。

## ADR-003：阶段回退增强范围 —— 跨级回退 + 历史表（a+b）

**状态**：已接受

**背景**：现状 `changePhase` 仅允许相邻推进/回退；无任何阶段历史记录（仅 operation_log 操作流水）。

**选项**：
- a) 仅新增历史表；
- b) 仅放开跨级回退；
- a+b) 两者都做（选定）；
- c) 都不做。

**决策**：选择 a+b。

**理由**：
1. 跨级回退是高频真实诉求（项目返工、流程纠错、误操作回退），相邻限制过于僵硬；
2. 历史表保证阶段轨迹可追溯、可审计，是跨级放开的安全前提；
3. 组合一次设计到位，避免二次返工。

**后果**：回退动作必须留痕（原因必填 + 历史表）；跨级回退需前端二次确认降低误触；`changePhase` 签名扩展（新增 reason 参数），调用方需同步。

## ADR-004：阶段历史表记录范围与 action_type 设计

**状态**：已接受

**决策**：`project_phase_history.action_type` 取值 `ADVANCE`（推进）/ `ROLLBACK`（相邻回退）/ `SKIP_ROLLBACK`（跨级回退），覆盖全部阶段变更动作。

**理由**：
1. 完整阶段轨迹便于审计与后续 UI 时间线展示；
2. `SKIP_ROLLBACK` 与 `ROLLBACK` 虽可由 from/to sort 差值推导，但冗余枚举便于直接查询跨级事件（审计关注点）；
3. 推进也入表，使历史表成为阶段变更的完整事实源（不依赖 operation_log 的文本流水）。

**后果**：推进操作多一次写入，成本可忽略；后续 UI 时间线可直接基于本表查询。

## ADR-005：回退原因必填约束

**状态**：已接受

**决策**：所有回退动作（相邻回退与跨级回退）reason 必填；前端必填校验 + 后端 `StringUtils.hasText` 兜底。

**理由**：回退是状态回滚，必须留下业务理由，否则审计无从谈起；推进方向不强制 reason（推进有材料校验兜底，属正常流程）。

**后果**：前端回退弹窗需包含原因输入框；后端接口契约扩展。
