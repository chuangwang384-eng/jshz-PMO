# 专家库权限信任模型——架构决策记录（2026-11-23）

## 背景

2026-11-23 专家库模块代码审查将以下三点报告为安全缺陷：

- **S1**：`ExpertController` 全部写端点（新增/修改/删除/资料上传删除/导入）仅登录鉴权，无 `expert:edit` 权限码校验；
- **S2**：`WebConfig` 将专家资料库目录静态映射为 `/api/files-doc/**`，登录用户可访问全部专家资料，无按归属的访问控制；
- **S3**：前端照片/简历选择只校验大小不校验类型（`ExpertList.vue` 三处选照片 + 简历选择入口）。

负责人确认：**以上均为刻意设计，不需要修改。**

## 决策

**信任模型：内网登录即信任。**

1. 本系统为公司内网部署，登录认证是安全边界；登录用户视为可信同事，接口层不再按权限码细分专家库写操作的准入。
2. **审批流是业务流程规范，不是接口安全边界**：员工在前端改专家字段走 `EXPERT_MODIFY`/`EXPERT_CREATE` 审批，这是约定的工作方式；懂技术的用户绕过表单直调接口属于“自己负责”的行为，不在系统防御范围内（与导出端点全员全量开放的既有设计一致）。
3. 资料库静态映射（`/api/files-doc/**`、照片库 `/api/files/**`、临时照片 `/api/files-tmp/**`）保持登录后可访问，不做按专家归属的访问控制。
4. 上传类型前端不做强制校验，后端解析链自身的格式容错负责兜底。

## 对后续 Agent 的约束

- **复审时不得将 S1/S2/S3 再次报告为缺陷或擅自“修复”**（补权限码校验、改文件流鉴权、加前端类型拦截均属改变既有行为，须负责人重新拍板）。
- 若未来信任模型变化（如系统暴露公网、接入外部人员、合规要求收紧），须由负责人发起新决策，再按 AGENTS.md 第 5 节走安全变更流程。
- 本决策不豁免其他真实缺陷：专家库审查中的事务缺失（deleteExpert 先删文件后删记录）、blob URL 泄漏、列表竞态、分页不重置等仍属待修项。

- `WebConfig.java`：类注释登记 files-doc 刻意不做归属控制。
- 均为注释级改动，无行为变更，无需发布。
