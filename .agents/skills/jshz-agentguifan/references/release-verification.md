# PMO 发布验证

1. **确认发布对象。** 读取仓库 `AGENTS.md`、`docs/deployment.md`、相关近期发布记录和本次发布脚本的参数。核对目标环境、源码提交及未提交改动、`version.txt`、实际待发布产物、配置与依赖差异。涉及生产切换或迁移时，按仓库流程确认授权、备份、维护窗口和回滚入口。
2. **在隔离目录验证改动。** 后端按当前 `backend/pom.xml` 和发布约定选择 JDK，当前基线为 17。用 `mvn -version` 核对 Maven 实际使用的 Java，再运行受影响的测试和仓库规定的构建。正式制品沿用仓库构建脚本及 `builds/` 隔离目录，避免对生产使用的 `backend/target` 原地构建。打包若跳过测试，另行记录实际测试范围和结果。涉及前端时，按 `frontend/package.json` 运行构建及适用检查。静态分析、覆盖率和依赖扫描按仓库已有配置或 CI 执行，记录适用性、结果和未运行原因。
3. **核对差异和预检结果。** 检查实际发布差异、版本及制品对应关系，重点看权限、环境变量、依赖和敏感信息。涉及数据库时验证新库基线与既有库增量，并核对迁移期间的应用版本兼容性和恢复方案。按当前脚本说明运行适用的预检。仓库要求的检查失败时，先处理失败项，再继续切换。
4. **核对线上实际版本。** 后端核实应用日志、数据库连接及直连和经 Nginx 的健康响应，核对 `/health` 的版本和可用的提交标识。前端核实 Nginx 发布目录、线上首页与静态资源可用性及实际加载的构建版本。异常时按本次发布的回滚方案处理，并复核恢复后的版本和服务状态。
5. **验证受影响的业务路径并留证。** 用获准账号核对登录、相关页面、关键 API 与权限。权限有变化时分别验证允许和拒绝路径。业务写入使用获准的环境和数据。发布记录分别写明构建与测试、生产技术冒烟、登录后业务验收的结果，标注版本、提交、环境及证据。缺少账号、业务数据或执行条件时，明确登记待验项及原因。
